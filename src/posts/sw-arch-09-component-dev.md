## 一、前端模块化概述

### 模块化分类

- **外部模块化** (External Modularization)：引入第三方包或插件，通常由一个或多个 JS 文件组成。
  - **设计思路**：现代前端开发不可能从零构建一切，外部模块化解决了"代码复用最大化"的问题——与其每个项目重复造轮子，不如直接引入社区成熟的解决方案，大幅降低开发成本和维护负担。
  - **设计目的**：实现跨项目的依赖共享与版本管理，体现"依赖倒置"思想——你的工程依赖抽象接口（NPM 包的 API）而非具体实现，使得第三方库可以独立演进而不破坏调用方代码。

- **内部模块化** (Internal Modularization)：工程内部的分层或分类，内部一个模块一般由一个 JS 文件表示。
  - **设计思路**：当项目代码量增长到数千行时，单文件维护会变得极其困难。内部模块化通过"分而治之"的策略，按职责将代码切分为独立文件，每个文件关注单一功能领域。
  - **设计目的**：追求高内聚低耦合——一个模块内部的函数和数据紧密相关（高内聚），而模块之间通过明确的接口通信（低耦合），从而提升代码的可维护性和可测试性。

### 模块化的主要内容

- 外部模块管理：`Node.js` 和 `NPM`（包管理器）。
  - **设计实现**：Node.js 提供运行时环境，NPM 提供包注册中心与命令行工具。NPM 通过 `package.json` 声明依赖和版本范围，`node_modules` 存放实际安装的包，`package-lock.json` 锁定精确版本号以保证团队协作时依赖一致性。
  - **设计目的**：建立标准化的依赖管理体系，使"安装-使用-升级-卸载"外部模块的整个生命周期可控、可复现，这是工程化"可重复构建"原则的具体体现。

- 内部模块组织：`CommonJS`、`ES6 Module` 和构建工具（Webpack 等）。
  - **设计思路**：浏览器原生不识别 `require` 或 `import`，因此需要一套"编写时"的模块规范加上"构建时"的打包工具。CommonJS（同步加载，适合服务端 Node.js）和 ES6 Module（静态导入，适合浏览器端 Tree Shaking）代表了两种不同的模块加载哲学。
  - **设计目的**：解决 JavaScript 长期以来"没有原生模块系统"的历史遗留问题，通过模块化语法让开发者显式声明依赖关系，使得静态分析工具、打包工具、IDE 都能自动理解代码结构并进行优化（如 Tree Shaking 剔除未使用代码）。

- 编译与转换：模块源码到目标代码，转译工具如 `Babel`。
  - **设计实现**：Babel 作为转译器（Transpiler），将 ES6+ 语法解析为 AST（抽象语法树），然后通过插件体系将新语法转换为 ES5 兼容代码。这个"解析-转换-生成"的三阶段流水线是可扩展的，任何开发者都可以编写 Babel 插件自定义语法转换规则。
  - **设计目的**：打破"开发者必须等待所有浏览器支持新语法才能使用"的困境，实现"用未来的 JavaScript 写今天的代码"。这是前端工程化"编译时 vs 运行时"分层思想的体现——在编译阶段解决兼容性，运行时无需任何 Polyfill 开销。

## 二、Promise 对象

### 基本概念

- Promise 是**异步编程**的解决方案，比传统 (事件 + 回调) 更合理强大。
  - **设计思路**：JavaScript 是单线程语言，I/O 操作（网络请求、文件读写、定时器）必须采用异步模式，否则会阻塞 UI 渲染导致页面卡死。传统的"事件监听 + 回调函数"方案在复杂异步流程中会导致代码嵌套失控，Promise 通过"状态机"的设计模式将异步操作的"发起"与"结果处理"解耦，从根本上改变了异步代码的组织方式。
  - **设计目的**：将异步操作对象化——将"一个异步操作的最终结果"抽象为一个一等公民对象，可以像普通值一样被传递、组合、链式调用，从而提升代码的表达能力和可组合性。

- 由社区最早提出，**ECMAScript 将其写入语言标准**，原生提供。
  - **设计目的**：标准化是避免社区分裂的关键。在 Promise 成为标准之前，jQuery 的 Deferred、Q、Bluebird 等多种异步方案并存，互不兼容。ECMAScript 统一标准后，所有浏览器和类库基于同一套 API 工作，降低了学习成本和迁移成本。

- Promise 是一个存取数据的**容器**，封装基于 `XMLHttpRequest` 异步请求后的状态和值。
  - **设计实现**：Promise 包装了一个"将来才会确定的值"，外部代码无法直接修改容器内部的值，只能通过 `.then()` 注册回调来获取。这种封装机制保证了异步结果不会被意外篡改，同时将"如何获取结果"的细节对外部透明。
  - **设计目的**：实现"关注点分离"——发起请求的代码不需要知道响应数据最终会被如何使用，处理响应的代码也不关心请求是如何发起的，二者通过 Promise 这个中间容器解耦。

- 从语法上说，Promise 是一个对象，提供**统一 API**，各种异步操作均可用相同方法处理。
  - **设计思路**："统一接口"是软件工程中最强大的抽象手段之一。无论是 HTTP 请求、文件读取、数据库查询还是定时器，都可以包装为 Promise，然后用同一套 `.then()/.catch()/.finally()` 链式语法处理。这种统一性意味着开发者只需学习一次 Promise 的使用模式，就能应对所有异步场景。

### 同步与异步

- **同步** (Synchronous)：代码顺序执行，上一步完成后才执行下一步。
  - **设计思路**：同步模型符合人类线性思维，代码执行顺序与书写顺序一致，调试直观。但在前端场景中，如果一个同步 HTTP 请求耗时 3 秒，整个页面会在这 3 秒内完全冻结（无法点击、滚动、输入），用户体验极差。因此同步仅适用于纯计算任务，不适合 I/O 密集型操作。

- **异步** (Asynchronous)：不等待上一步完成即继续执行。
  - **设计实现**：JavaScript 通过"事件循环"（Event Loop）机制实现异步。异步操作会被委托给浏览器的底层 API（如网络线程、定时器线程），主线程继续执行后续代码。当异步操作完成后，其回调被放入"任务队列"，等主线程空闲时再从队列取出执行。

- 核心问题：**异步代码无法通过 `return` 返回值**。
  - **设计思路**：这个问题的根源在于执行时序的不匹配——`return` 发生在当前函数调用栈内（同步时刻），而异步结果在未来的某个时间点才到达（异步时刻）。因此异步编程必须通过回调函数或 Promise 等机制将"对结果的处理逻辑"注册到未来执行，这是 Promise 设计的最原始动机。

### 回调函数的问题

- 回调函数 (Callback) 是异步编程的早期方案：将后续逻辑作为函数参数传入。
  - **设计实现**：回调方案本质上是通过"函数指针"（将函数作为参数传递）来延后执行。在 Node.js 中形成了约定俗成的 error-first 回调风格 `function(err, data) {}`，这使得错误处理有章可循但缺乏语言层面的强制力。

- 多次嵌套回调造成**回调地狱** (Callback Hell)：代码层层缩进，可读性差，调试困难，维护成本高。
  - **设计思路**：回调地狱的深层原因是"控制反转"（Inversion of Control）——当前函数将自己的一部分逻辑委托给异步 API，却无法控制回调何时被调用、调用多少次、以什么参数调用。Promise 通过"状态固化"解决这一问题：Promise 状态一旦确定就不会再变，保证回调只会被正确调用一次。
  - **设计目的**：Promise 的链式调用将"嵌套"变为"串联"，将横向缩进转为纵向展开，本质上是将"控制权"从被调用方收回给调用方，让开发者重新掌控异步流程的编排权。

### Promise 基本用法

- 构造函数**必须有一个函数作为参数**：`new Promise((resolve, reject) => {...})`
  - **设计实现**：这个函数参数被称为"执行器"（Executor），它在 Promise 构造时立即同步执行。执行器的职责是启动异步操作，并在操作成功或失败时分别调用 `resolve` 或 `reject`。这种设计将"启动异步"与"处理结果"在空间上分离，在时间上串联。
  - **设计目的**：执行器模式保证了异步操作在 Promise 创建时就立刻开始执行（而不是等到 `.then()` 调用时才启动），这意味着 Promise 代表的是"一个已经在进行中的异步操作的结果"，这也被称为"热"（Hot）异步模式。

- 该函数的两个参数 `resolve` 和 `reject` 也是函数：分别在**成功**和**失败**时调用进行存值。
  - **设计思路**：`resolve` 和 `reject` 是 Promise 内部提供给执行器的"回调钩子"，它们本质上改变了 Promise 的内部状态（`PromiseState`）并存储结果值（`PromiseResult`）。这一设计遵循"单一出口"原则——无论异步操作内部多么复杂，最终只有两条路径：成功或失败。

- 通过实例的 `.then()` 方法中的两个回调分别在成功时**取值**或失败时**处理**。
  - **设计目的**：`.then(onFulfilled, onRejected)` 提供了对两种结果路径的对称处理能力。这种对称性使得异步流程的分支逻辑与同步代码的 `try-catch` 模式在结构上对齐，降低了认知负担。

- Promise 对象维护两个内部属性：
  - `PromiseResult`：保存异步结果的值。
  - `PromiseState`：保存状态 (pending / fulfilled / rejected)。
  - **设计实现**：这两个内部属性对外部代码是不可直接访问的（封装性），只能通过 `.then()` 方法间接获取。这个设计保证了状态的不可篡改性——外部代码无法通过赋值操作强行改变 Promise 的决议结果，维护了异步流程的可靠性。

- `.then()` 监听 `PromiseState` 的变化，选择对应的回调执行。
  - **设计实现**：这里的"监听"并非轮询（Polling），而是基于微任务队列（Microtask Queue）的事件驱动机制。当 `resolve` 或 `reject` 被调用时，Promise 会将其 `.then()` 注册的回调作为微任务入队，在当前宏任务结束后、下一个宏任务开始前执行。这一机制保证了回调执行的时机精确且可预测。

### Promise 的三种状态

| 状态 | 含义 | 说明 |
|------|------|------|
| `pending` | 进行中 | 初始状态，既未成功也未失败 |
| `fulfilled` | 已成功 | 操作成功完成 |
| `rejected` | 已失败 | 操作失败 |

- **设计思路**：三状态模型借鉴了"有限状态机"（Finite State Machine）的设计模式。每个 Promise 在任何时刻只能处于三个状态之一，且状态转换具有严格的方向性——只能从 `pending` 出发，到达 `fulfilled` 或 `rejected` 后永久停留在目标状态。这种"确定性"是 Promise 可靠性的根基。

### Promise 的主要特点

1. **状态不受外界影响**：只有异步操作的结果可决定状态，任何其他操作无法改变。
   - **设计目的**：这一特性实现了异步操作的"自治性"——Promise 是对真实异步过程的忠实映射，外部代码无法"伪造"成功或"掩盖"失败，保证了数据流的真实性和可信任性。在设计哲学上，这是"单一数据源"（Single Source of Truth）原则在异步场景的体现。

2. **状态一旦改变就凝固**：
   - 只能从 `pending` -> `fulfilled`，或 `pending` -> `rejected`。
   - 改变后不再变化，此时称为 **resolved**（已定型）。
   - **设计实现**：状态凝固是通过内部标志位实现的——一旦 `PromiseState` 被设置为非 `pending` 值，后续对 `resolve` 或 `reject` 的任何调用都会被静默忽略。这种"不可变性"（Immutability）设计消除了"回调可能被多次触发"的隐患，是 Promise 优于纯回调方案的核心技术优势之一。

3. **定型后可立即取值**：与事件不同，即使状态已定型，再添加回调函数，也会**立即得到结果**。
   - **设计实现**：Promise 在内部缓存了定型后的结果值。当 `.then()` 被调用时，Promise 首先检查自身状态——如果已经 resolved，则立即将缓存的回调加入微任务队列以期尽快执行；如果仍 pending，则将回调注册到等待列表。这一机制使得 Promise 既能处理"先 resolve 后 then"的场景，也能处理"先 then 后 resolve"的场景，消除了事件模型中"错过触发时机"的问题。
   - **设计目的**：这是 Promise 与 DOM 事件的核心区别——事件代表"发生过的动作"，错过了就无法再触发；Promise 代表"操作的结果"，结果一旦存在就永远不会消失，任意时刻都可以获取。这种"结果持久化"特性使得异步操作的消费者无需关心操作的时序，极大地简化了代码的时序逻辑。

### 使用范例要点

- 范例一：基本创建与使用，演示 `resolve`/`reject` 和 `.then()` 的配合。
  - **设计思路**：基本范例的目的是建立"创建-决议-消费"的心智模型。`new Promise` 创建容器并启动异步流程，`resolve/reject` 决议结果，`.then()` 消费结果。这三个环节对应了异步操作的完整生命周期。

- 范例二：结合 `setTimeout` 模拟异步场景。
  - **设计实现**：`setTimeout` 是最简单的异步 API，通过它可以可控地在指定延迟后调用 `resolve`，模拟网络延迟等真实场景。这体现了 Promise 的通用性——任何回调风格的异步 API 都可以通过 Promise 构造函数包装，从而进入 Promise 的链式调用生态。

### 链式调用

- `.then()` 返回**新的 Promise 对象**，实现链式调用 (Chaining)。
  - **设计实现**：每次调用 `.then()` 都会创建一个全新的 Promise，这个新 Promise 的决议取决于 `.then()` 中回调函数的执行结果。如果回调返回一个普通值，新 Promise 以该值 fulfilled；如果回调返回一个 Promise，新 Promise 会"跟随"（follow）该 Promise 的状态；如果回调抛出异常，新 Promise 以该异常 rejected。这种递归性的设计是链式调用的基石。
  - **设计目的**：每个 `.then()` 返回新 Promise 而非修改原 Promise，体现了"不可变性"——避免副作用，使同一个 Promise 可以被多个消费者独立订阅而互不干扰。

- 用链式调用**替代回调函数嵌套**，使代码扁平化，消除回调地狱。
  - **设计思路**：链式调用将"深度嵌套"转化为"顺序串联"，本质上是将异步流程的"纵向复杂度"转换为"横向可读性"。这并非只是语法美化，而是一种控制流抽象——将原本手动管理的多层回调关系抽象为一段线性声明式代码。

- 每个 `.then()` 中的返回值会作为下一个 `.then()` 的输入。
  - **设计目的**：这种"值传递"机制使 Promise 链成为一个"异步处理管道"（Pipeline），每一步处理上一步的输出并传递给下一步，类似于函数式编程中的 `pipe` / `compose` 模式。这使得复杂的数据转换流程可以被拆解为多个可复用的小步骤。

### Promise 的其他 API

- `Promise.prototype.catch()`：专门捕获 rejected 状态，等价于 `.then(null, onRejected)`。
  - **设计思路**：语义化的 API 设计——`catch` 比 `then(null, fn)` 更能表达"这是错误处理分支"的意图。这使代码自文档化，降低阅读者的理解成本。此外，`.catch()` 在链式调用末尾可以作为"安全网"，捕获链上任何一步抛出的错误，避免未处理的 Promise rejection。

- `Promise.prototype.finally()`：无论 fulfilled 或 rejected，最终都会执行的回调。
  - **设计实现**：`.finally()` 的回调不接受任何参数（不知道 Promise 的结果是成功还是失败），它的返回值和返回的 Promise 通常不影响链的后续。主要用于资源清理场景，如关闭 loading 指示器、断开数据库连接、释放文件句柄等。
  - **设计目的**：`finally` 的设计源于"资源管理"的通用需求——无论操作成败，某些清理工作必须执行。它将清理逻辑与成功/失败的业务逻辑分离，遵循"关注点分离"原则，避免了在 `then` 和 `catch` 中重复编写清理代码。

- `Promise.all(iterable)`：接受 Promise 数组，**全部成功**则返回结果数组；**任一失败**则整体 rejected。
  - **设计实现**：`Promise.all` 内部维护一个计数器和一个结果数组。每个子 Promise resolve 时，计数加一并将结果插入对应位置（保证结果顺序与输入顺序一致，而非完成顺序）。所有子 Promise 都 resolve 后，`Promise.all` 以完整结果数组 resolve。任一子 Promise reject 则立即短路，整体以该错误 reject。
  - **设计目的**：解决"并行执行、统合结果"的场景——多个独立异步操作可以同时发起以节省总耗时，但需要所有结果都到位后才能进行下一步处理。典型的"扇出-扇入"（Fan-out / Fan-in）并发模式。常见于需要同时请求多个 API 数据然后聚合渲染的页面。
  - **设计思路**："快速失败"（Fail-fast）是 `Promise.all` 的重要设计决策——一旦任一子任务失败，不再等待其他任务完成，立即返回失败。这种策略适合"全部成功才有意义"的场景（如提交事务）。对于需要"部分成功也接受"的场景，应使用 `Promise.allSettled`。

## 三、async / await 关键字

### async 关键字

- 用于快速创建异步函数，是 Promise 的**语法糖** (Syntactic Sugar)。
  - **设计思路**："语法糖"并非"可有可无的装饰"，它降低了抽象的使用门槛。Promise 的 `.then()` 链虽然解决了回调地狱，但仍要求开发者以"链式声明"的方式思考，与同步代码的直觉有显著差距。`async/await` 在此基础上更进一步——让异步代码看起来和同步代码几乎一模一样，彻底消除心智切换的成本。
  - **设计目的**：降低异步编程的认知复杂度，使异步代码的编写者和阅读者都可以用线性的、顺序的方式理解代码逻辑，而不需要在脑中构建 Promise 链的事件时序图。这是"声明式编程"理念的一次重要实践——"你想要什么结果"比"过程如何编排"被更清晰地表达。

- 实际使用中，`async` 与 `await` 组合实现**异步向同步的转换**。
  - **设计实现**：`async` 函数被调用时，函数体执行到第一个 `await` 时将控制权交还给调用方（不阻塞主线程），同时函数体剩余部分被隐式包装为 Promise 的 `.then()` 回调。当 `await` 的 Promise resolve 后，剩余代码作为微任务继续执行。这本质上是对 Generator + Promise 模式的进一步封装和简化。

- `async` 函数始终返回一个 Promise 对象。
  - **设计实现**：即使 `async` 函数内部使用 `return 'hello'` 返回一个普通字符串，JavaScript 引擎也会自动将其包装为 `Promise.resolve('hello')`。同样，如果函数内部抛出异常，会被自动捕获并转换为 `Promise.reject(error)`。这种自动包装保证了 `async` 函数与 Promise 生态的无缝兼容——调用者永远可以用 `.then()/.catch()` 或 `await` 来处理 `async` 函数的返回值。

### await 关键字

- `await` 调用异步函数时**阻塞当前执行流**，等待异步函数执行结束。
  - **设计实现**：这里的"阻塞"是对 `async` 函数内部而言的，对主线程不阻塞。`await` 的实现原理是——将函数体在 `await` 处"暂停"（suspend），将后续代码注册为被等待 Promise 的 `.then()` 回调，然后立即将控制权交还给 JavaScript 事件循环。这类似于 Generator 函数的 `yield` 机制，但语义更专注于异步等待。

- 自动从返回的 Promise 对象中**取值并返回**。
  - **设计思路**：`await` 消除了手动调用 `.then()` 获取 Promise 结果值的心智负担。开发者可以直接将 `const data = await fetch(url)` 的结果当作同步数据使用。这种"透明性"是语法糖的核心价值——它让开发者不再需要区分"这是普通值还是 Promise 包裹的值"。

- **使用规则**：
  - 只能用于 `async` 声明的异步函数中。
  - 只阻塞 `async` 函数**内部**代码，不阻塞外部代码。
  - **设计目的**：这两条规则相互配合，保证了异步编程的安全边界。"只能用于 async 函数"确保了开发者明确标识了异步上下文；"只阻塞内部不阻塞外部"保证了与 Promise 现有生态的完全兼容，不会因为引入 `await` 而改变已有的调用约定。

- **优点**：用**同步的方式**编写和使用异步，代码可读性大幅提升。
  - **设计目的**：可读性不仅是"看起来更好看"，它直接关系到代码的维护成本和缺陷率。同步风格的异步代码使得条件分支（if-else）、循环（for/while）、异常处理（try-catch）都可以用标准语法编写，而不需要学习 Promise 特有的变体（如 `Promise.all` 对应循环，链式 `.then` 对应顺序语句）。这极大地降低了团队中初级开发者的学习曲线。

- **缺点**：reject 回调被自动忽略，必须用额外的 `try-catch` 处理失败。
  - **设计思路**：这是 `async/await` 将异步代码同步化带来的自然代价——同步代码中用 `try-catch` 处理错误，异步代码也应该用同样的方式。这种一致性实际上是优点：不再需要混合使用 `.catch()` 和 `try-catch` 两套错误处理机制。但开发者需要意识到，如果没有 `try-catch` 包裹 `await` 表达式，Promise rejection 会变成未捕获的异常。

### async/await 使用注意事项

- 将嵌套的 `.then()` 链改写为顺序 `await` 调用，代码更符合直觉。
  - **设计实现**：改写遵循一一对应原则：`.then(onFulfilled)` 中的回调函数体变为 `await` 之后的代码，`.catch(onRejected)` 变为 `catch(err)` 块。这种机械转换是"语法糖"的直接体现——底层运行机制完全相同，只是表达方式变化。

- 注意**并行 vs 串行**：多个不相关异步操作应用 `Promise.all()` 并行执行，避免不必要的串行等待。
  - **设计思路**：`await` 默认是串行的（等待上一个完成再执行下一个），如果不加思考地对多个独立异步操作使用多个 `await`，会导致总耗时等于各操作耗时之和，浪费了并行带来的性能收益。正确做法是将独立操作以 `Promise.all` 包裹后再 `await`，这是从"写法正确"到"性能正确"的关键一步。
  - **设计目的**：提示开发者理解 `await` 的本质语义——"我需要这个结果才能继续"，而非"我先等一等"。如果一个 `await` 不依赖上一个 `await` 的结果，就应该考虑并行化。性能优化不需要引入额外工具，只需要合理排列 `await` 和 `Promise.all`。

- 需要准确理解执行顺序：`await` 后的代码等价于 `.then()` 中的回调。
  - **设计实现**：`await` 将函数体在当前位置分为两部分——`await` 之前的代码在函数调用时立即同步执行，`await` 之后的代码被延迟到 Promise resolve 后作为微任务执行。这意味着 `await` 之前的代码运行在当前宏任务中，`await` 之后的代码运行在未来的微任务中，理解这一时序对于调试复杂的异步执行顺序至关重要。

## 四、Fetch API

### 什么是 Fetch API

- `fetch()` 是 `XMLHttpRequest` 的**升级版**，用于在 JS 中发出异步 HTTP 请求。
  - **设计思路**：`XMLHttpRequest` (XHR) 诞生于 2000 年前后的 AJAX 时代，API 设计过时——基于事件（`onreadystatechange`）而非 Promise，不支持流式处理。随着 Web 应用从"服务器渲染页面"向"客户端 SPA"演进，HTTP 请求的频率和复杂度大幅增加，迫切需要一套现代化的请求 API。`fetch()` 的设计从零开始，没有 XHR 的历史包袱，以 Promise 和 Stream 等新标准为基础。
  - **设计目的**：将 HTTP 请求从"事件驱动的状态机模型"升级为"Promise 驱动的函数调用模型"，将复杂的请求声明简化为一个函数调用加上链式处理。

- 归属于**ES6 标准**规范，绝大部分现代浏览器原生支持。
  - **设计目的**：作为 Web 平台标准的一部分，`fetch` 的标准化意味着它与 Service Worker、Cache API、Streams API 等 Web API 共享同一套底层基础设施（如 Request/Response 对象），形成了完整的"Web 请求生态"。这种生态一致性使得多个 API 可以无缝组合使用。

- 基于**Promise 对象**实现，极大简化异步请求代码。
  - **设计实现**：`fetch(url)` 调用直接返回一个 Promise，开发者无需手动创建 Promise 包装 XHR。请求发起、响应处理和错误捕获全部通过统一的 Promise 链完成，与 `async/await` 天然兼容。

### fetch() 发送请求

- 完整语法：`fetch(url, optionObject)`
  - **设计实现**：`optionObject`（通常命名为 `init`）是一个配置对象，支持 `method`、`headers`、`body`、`mode`（CORS 模式）、`credentials`（Cookie 策略）、`cache`、`redirect` 等丰富的请求控制选项。这种"选项对象"模式（Options Object Pattern）使得 API 具有良好的可扩展性——未来新增配置项不需要改变函数签名。

- GET 请求：可省略 `optionObject`。
  - **设计思路**：最常见的请求场景（GET 获取数据）被优化为最简洁的调用形式 `fetch(url)`。这种"易用性优先"的 API 设计降低了入门门槛，让简单的任务保持简单。

- POST 请求：在 `optionObject` 中指定 `method: 'POST'`、`headers`、`body` 等。
  - **设计实现**：与 GET 的统一表达模式——所有请求类型共享同一套配置格式，只是 `optionObject` 中具体字段的值不同。这种一致性遵循"最少意外原则"，开发者学习一次配置结构即可处理各种 HTTP 方法。

### fetch() 的响应对象

- `fetch()` 返回一个 **Response 对象**（Promise 包装）。
  - **设计实现**：Response 对象是 Fetch API 的核心抽象，封装了 HTTP 响应的所有信息——状态码、响应头、响应体和与请求的关联。它将原本在 XHR 中分散在 `status`、`responseText`、`getResponseHeader()` 等多个属性和方法的信息统一到一个对象中，体现了"高内聚"的设计原则。

- 常用属性和方法：
  - `Response.ok` —— 布尔值，2xx 为 `true`，其他 `false`。
  - `Response.status` —— 整型，真实 HTTP 状态码。
  - `response.text()` —— 返回文本字符串（返回 Promise）。
  - `response.json()` —— 返回 JSON 对象（返回 Promise）。
  - `Response.clone()` —— 底层通过 Stream 流实现，只能**读取一次**，clone() 创建副本。
  - **设计思路**：Response body 设计为一次性 Stream 读取（而非像 XHR 的 `responseText` 那样可以反复读取），这是因为 Fetch API 底层使用了 ReadableStream。流式设计的优势在于可以处理超大响应体（不一次性加载到内存）和实现渐进式渲染，代价是需要 clone 才能多次读取。
  - **设计目的**：Stream 模式使前端可以处理文件下载、视频流等大数据场景，而不必担心内存溢出。`clone()` 方法为"需要多次读取"的场景提供了安全的解决方案，确保原始 Stream 数据不被消耗。

## 五、Axios 库

### Axios 简介

- 基于 Promise 的**第三方 HTTP 库**，可用于浏览器和 Node.js。
  - **设计思路**：跨平台的 HTTP 调用面临不同的底层实现——浏览器端使用 `XMLHttpRequest`，Node.js 端使用 `http` 模块。Axios 通过"适配器模式"（Adapter Pattern）封装了这种平台差异：在浏览器端自动使用 XHR，在 Node.js 端自动使用 `http` 模块，但暴露给开发者的 API 完全一致。这种设计使得同一套代码可以在前后端共享，这是"同构"（Isomorphic）思想的体现。

- 本质上是对原生 XHR 的封装，用 Promise 实现。
  - **设计目的**：封装（Encapsulation）隐藏了 XHR 的复杂性——开发者不再需要手动管理 `readyState` 变化、监听 `onload/onerror` 事件、手动解析 JSON 字符串。Axios 将这些底层细节统一到 Promise 接口中，使得 HTTP 请求的使用体验与 `fetch` 一样简洁，同时提供更丰富的企业级功能。

- Axios 封装后提供更便捷的 API：
  - **拦截请求和响应** (Interceptors)：统一添加 token、日志、错误处理等。
    - **设计实现**：拦截器采用"中间件管道"（Middleware Pipeline）模式——请求拦截器按照注册顺序的正向执行（先注册的先执行），响应拦截器按反向执行（后注册的先执行）。这种类似洋葱模型的设计使得多个拦截器可以协同工作，例如：拦截器 A 添加 token，拦截器 B 记录日志，拦截器 C 处理 401 错误自动刷新 token，形成一个完整的请求预处理和后处理流水线。
    - **设计目的**：将"横切关注点"（Cross-cutting Concerns）从业务代码中抽离。在大型项目中，每个请求都可能需要携带认证信息、记录日志、统一错误提示。如果没有拦截器，这些逻辑会散布在每个请求调用处，造成严重的代码重复。拦截器将这些通用逻辑集中管理，大大降低了维护成本。
  - **转换请求/响应数据** (Transform)。
    - **设计目的**：允许在数据发送前或接收后进行自定义转换，例如将 JS 对象序列化为特定格式的 XML、对敏感数据进行加密/脱敏、将后端返回的特定格式数据转换为前端友好的数据结构。将转换逻辑与请求逻辑分离，提高了代码的可测试性。
  - **自动转换 JSON** 数据。
    - **设计实现**：Axios 在发送请求时自动将 `data` 字段的 JS 对象序列化为 JSON 字符串，并设置 `Content-Type: application/json`；接收响应时自动检测 Content-Type 并将 JSON 字符串解析为 JS 对象。这消除了最频繁的手工操作，使得开发者能直接关注业务数据而非数据格式。

### Axios 使用范例要点

- `axios.get(url)` / `axios.post(url, data)` 直接返回 Promise。
  - **设计思路**：Axios 将常用的 HTTP 方法映射为同名函数（`get`、`post`、`put`、`delete`、`patch` 等），遵循"约定优于配置"原则，让开发者的意图一目了然。直接返回 Promise 意味着可以无缝使用 `async/await`。

- 通过 `axios.create({baseURL, timeout})` 创建带默认配置的实例。
  - **设计实现**：`axios.create()` 返回一个带有预配置的 Axios 实例，该实例可以拥有独立的默认 `baseURL`、`timeout`、`headers` 等。这支持了"实例模式"（Instance Pattern）——在项目中为不同的后端服务创建各自的 Axios 实例，每个实例有独立的配置和拦截器，互不干扰。这是微服务架构下前端请求管理的常见模式。
  - **设计目的**：避免在每个请求中重复指定相同的配置参数（如服务器地址、超时时间），提高代码复用性和可维护性。

- 通过拦截器统一处理请求/响应逻辑。
  - **设计目的**：拦截器是 Axios 最具工程价值的特性之一。通过在单个位置定义拦截器，可以实现全局的请求加载状态管理（显示/隐藏 loading 动画）、统一的错误处理和用户提示（如网络错误提示、登录过期自动跳转）、以及自动刷新 token 等高级功能，这些在原生 Fetch API 中需要开发者自行实现。

## 六、Fetch API 与 Axios 对比

### Fetch API

- **优点**：
  - 原生支持，无需额外依赖。
    - **设计目的**：零依赖意味着零引入成本——不需要 npm install、不需要担心版本冲突、不需要担心包体积膨胀。对于轻量级项目或只需要少量 HTTP 请求的场景，原生方案是权衡复杂性与需求的合理选择。这也意味着 Fetch 有最长的兼容周期——标准一旦确立，就不会像第三方库那样因维护者的变化而产生不确定因素。
  - Promise 风格，比 XHR 更简洁。
    - **设计思路**：从事件模型到 Promise 模型的转变不仅是 API 表面的变化，更是编程范式的升级。Promise 的可组合性（`Promise.all`、`Promise.race`、`Promise.allSettled`）使得复杂请求编排（并行请求、竞速请求、批量请求）可以用声明式方式表达，而 XHR 时代这些场景需要大量的样板代码和状态追踪。
  - 现代化设计，支持 `async/await`。
    - **设计目的**：作为 ES6 标准的一部分，Fetch 与同期引入的 `async/await`、Promise、Streams API 等原生兼容，形成了完整的现代异步编程体系。这种设计一致性意味着技术栈整体升级时不会出现不兼容的问题。
  - **流式处理** (ReadableStream)：适合大文件和渐进式加载。
    - **设计实现**：Response.body 是一个 ReadableStream，可以通过 `getReader()` 获取 reader，逐步读取数据块。这使得前端可以处理流式数据场景：视频播放的 Range 请求、大文件下载的进度显示、服务端推送事件（SSE）的流式解析等。
- **缺点**：
  - 不自动处理 JSON：需手动调用 `res.json()`。
    - **设计思路**：Fetch 将"读取响应体"和"解析格式"分离为两步操作，这种"懒解析"（Lazy Parsing）设计提供了灵活性——你可以根据响应头中的 Content-Type 动态选择 `json()`、`text()`、`blob()` 或 `arrayBuffer()` 来读取。代价是增加了常见场景（JSON API）的代码量。
  - **错误处理不友好**：只对网络错误 reject，HTTP 错误码（404、500）不会抛错，需手动检查 `response.ok`。
    - **设计思路**：Fetch 遵循"HTTP 错误也是有效响应"的哲学——从网络层面看，服务器返回了 404 是正常的 HTTP 通信，只有 DNS 解析失败、连接超时等才是真正的网络异常。这种区分在需要精确处理不同 HTTP 状态码的场景下更有优势，但确实使得"快速失败"的默认模式需要额外代码。
  - 不支持请求取消（早期），现需 `AbortController`。
    - **设计实现**：`AbortController` 是较晚引入的 Web API，通过 `signal` 属性与 `fetch` 的 `signal` 选项连接。当 `abortController.abort()` 被调用时，fetch 请求被取消，Promise 以 `AbortError` reject。这是一种"协作式取消"模式——取消信号由外部控制器发出，被取消的操作通过检查信号状态来响应。
  - 缺乏对旧浏览器（如 IE）的支持。
    - **设计目的**：作为现代 Web 标准，Fetch API 明确放弃了对 IE 的兼容（IE 完全不支持 Promise，而 Fetch 基于 Promise）。项目的浏览器支持策略决定了能否直接使用 Fetch——如果必须支持 IE，要么使用 Polyfill，要么选择 Axios。

### Axios

- **优点**：
  - 自动转换 JSON，请求和响应自动序列化/反序列化。
    - **设计目的**：JSON 是 RESTful API 的事实标准格式，Axios 将 JSON 的序列化与反序列化作为默认行为，减少开发者每处调用都要手动处理格式转换的重复劳动。这种"智能默认"的设计理念使得常见场景开箱即用。
  - **更友好的错误处理**：HTTP 错误自动进入 `.catch()`。
    - **设计思路**：Axios 将任何非 2xx 的 HTTP 状态码视为错误（通过 `validateStatus` 配置可自定义），自动 reject。这与大多数业务场景的预期一致——后端返回 400/500 时通常意味着业务逻辑出错，理应进入错误处理分支。这是"实用主义"优先于"哲学纯粹性"的设计选择。
  - 支持请求取消：`CancelToken` 或 `AbortController`。
    - **设计实现**：Axios 在 Fetch 的 `AbortController` 标准化之前就提供了 `CancelToken` 方案。`CancelToken` 通过工厂函数创建，提供 `cancel` 方法和 `token` 对象，原理是在请求配置中注入一个内部的 cancel Promise，当 `cancel` 被调用时触发该 Promise reject。`AbortController` 的支持是后来增加的。
  - 请求和响应拦截器。
    - **设计目的**：拦截器是 Axios 最核心的工程化特性。在大型前端项目中，几乎每个 HTTP 请求都需要经过多层通用处理：认证（添加 token）、监控（记录耗时）、错误处理（统一 toast 提示）、重试（失败自动重试）。拦截器将这些"横切关注点"以可插拔的方式组织起来，形成了类似服务端中间件的灵活架构。
  - 更丰富的配置项：超时、请求头、转换函数等。
    - **设计目的**：丰富的配置使得 Axios 适用于从简单到复杂的各种场景，不需要随着需求升级而更换 HTTP 库。一个项目从简单的 GET 请求发展到复杂的流式上传、断点续传，配置项可以直接覆盖新需求，而非引入新依赖。
  - 更好的浏览器兼容性。
    - **设计实现**：Axios 内部使用 XHR 作为底层实现（浏览器端），XHR 是比 Fetch 更古老但兼容性更广泛的 API。这意味着 Axios 可以在 IE 11 等不支持 Fetch 的浏览器中正常工作，对需要广泛兼容的企业级项目尤为重要。
- **缺点**：
  - 需要额外引入库（增加体积和依赖）。
    - **设计思路**：每个依赖都有成本——初始加载体积增加（影响首屏性能）、版本升级可能引入 Breaking Change（增加维护工作量）、存在供应链风险（npm 包被恶意篡改或废弃）。在移动端或对首屏性能要求极高的场景，可能更倾向于使用原生 Fetch。
  - 非原生 API，项目越大依赖问题越明显。
    - **设计目的**：第三方库的生命周期不受你的控制——作者可能停止维护、API 可能大幅变更、安全漏洞可能被发现。当项目体量增大时，对第三方库的依赖风险也相应放大。相比之下，原生 API 随浏览器标准演进，有整个 Web 生态作为后盾，生命周期远超任何单个第三方库。

## 七、项目案例与前端项目演进

### 项目案例：宠物商城首页

贯穿全章的实践案例，展示前端项目从零到组件化的完整流程。

- **设计思路**：选择"宠物商城首页"作为贯穿案例，因为它涵盖了前端开发中最具代表性的场景——商品展示、用户交互、异步数据加载、组件拆分。通过一个完整案例串联所有知识点（异步请求、模块化、打包），避免了孤立教学带来的"学了不会用"的困境，体现了"项目驱动教学"的方法论。
- **设计目的**：案例教学的目的不是让学习者记住宠物商城的代码，而是建立从"业务需求"到"技术方案"到"工程实现"的完整思维链路。学习者可以将这一方法论迁移到任何前端项目中。

### 第一步：JavaScript 功能拆解

- 将整体业务逻辑拆分为独立功能模块。
  - **设计思路**：功能拆解是"自上而下设计"（Top-Down Design）的体现——先站在全局视角将系统分解为功能块，再逐一实现。拆解的粒度需要平衡：过细会导致文件碎片化，过粗则无法形成有效的模块边界。通常以"一个功能模块可被一个开发者独立开发和测试"为标准来判断粒度是否合适。

- 每个功能由一个或多个 JS 文件负责。
  - **设计实现**：物理层面，一个文件对应一个模块；逻辑层面，一个模块暴露有限的公开接口（export），隐藏内部实现细节。这种"封装"是模块化的核心价值——模块内部的修改不会影响其他模块，只要公开接口保持不变。

- 理清模块间的**依赖关系**和调用顺序。
  - **设计目的**：依赖关系的梳理直接影响到加载策略和构建配置。模块 A 依赖模块 B 时，B 必须在 A 之前加载和初始化。复杂的依赖关系应被可视化为"依赖图"（Dependency Graph），这是 Webpack 等构建工具的输入——工具通过分析依赖图决定打包顺序和代码分割策略。

- 拆解使代码组织清晰，便于维护和复用。
  - **设计目的**："清晰的组织"让新加入项目的开发者能快速定位目标代码（"商品列表功能在 product-list.js 中"）；"便于维护"让 bug 修复的影响范围可预测（"只改 cart.js 不会影响 user.js"）；"便于复用"让通用的工具模块被多个功能引用而非复制粘贴。这三者是模块化设计的核心价值体现。

### 第二步：静态资源打包

- 使用构建工具（Webpack、Vite 等）对静态资源进行**打包** (Bundle)。
  - **设计思路**：浏览器有 HTTP/1.1 并发连接数限制（通常每个域名 6 个），加载大量小文件（几十个 JS 模块）会导致请求排队，总加载时间远超单一大文件的加载时间。打包将多个小文件合并为一个或几个 Bundle，大幅减少 HTTP 请求数量。Vite 等新一代工具更进一步——开发阶段使用原生 ES Module 按需加载（利用浏览器原生 import），生产阶段才用 Rollup 打包，兼顾了开发体验和生产性能。
  - **设计目的**：打包不仅是"合并文件"，更是"编译时优化"的入口——代码压缩（Minification）、无用代码剔除（Tree Shaking）、作用域提升（Scope Hoisting）、代码分割（Code Splitting）等优化都发生在打包阶段。

- 目的：合并文件、压缩体积、语法转换 (`Babel`)、优化加载性能。
  - **设计实现**：现代构建工具通过"加载器"（Loader）+ "插件"（Plugin）的体系组织这些转换。Loader 负责文件转换（如 Babel Loader 将 ES6 转为 ES5，CSS Loader 将 CSS 转为 JS 模块），Plugin 负责更宽泛的任务（如生成 HTML 文件、注入环境变量、生成 Service Worker）。这种可插拔架构使构建流程可高度定制。

- 减少 HTTP 请求次数，提升页面加载速度。
  - **设计目的**：减少 HTTP 请求是 Web 性能优化的基本原则之一。虽然 HTTP/2 和 HTTP/3 的多路复用缓解了并发连接瓶颈，但文件合并仍能减少请求头的冗余传输并提高压缩效率。更重要的是，打包后的代码可以进一步优化——通过 Tree Shaking 剔除未使用的代码（一个大型第三方库只用到其中几个函数，打包后只保留用到的部分），这是模块级别的依赖分析才能实现的优化。

### 第三步：模块化和组件化

- **模块化** (Modularization)：按功能划分代码，一个模块对应一个 JS 文件，关注代码组织和复用。
  - **设计思路**：模块化的划分维度是"功能"（What does it do?），例如"用户认证模块"、"数据缓存模块"、"路由模块"。这种划分与 UI 无关，模块可以是纯逻辑的（不渲染任何 DOM）。模块化的关注点是代码层面的可维护性——如何让业务逻辑不纠缠在一起，如何让单元测试可以独立运行。
  - **设计目的**：实现"关注点分离"（Separation of Concerns）——不同功能的代码位于不同模块，每个模块可以独立开发、测试、版本管理。这是软件工程最基础也最重要的原则之一。

- **组件化** (Componentization)：按视觉/交互单元划分，一个组件包含 HTML + CSS + JS，关注 UI 封装和复用。
  - **设计思路**：组件化的划分维度是"界面"（What does it look like / What does it do on screen?），例如"导航栏组件"、"商品卡片组件"、"模态框组件"。每个组件是一个自包含的 UI 单元——有自己的模板（结构）、样式（外观）和逻辑（行为），三者封装在一起。这种封装使得组件可以像"乐高积木"一样被组装成页面。
  - **设计目的**：组件化的核心目标是 UI 的"复用性"和"可组装性"——同一个"评分星星"组件可以用在商品详情页、评论列表页、用户评价页，而不需要每处重新实现。同时，组件作为抽象单元，使得设计与开发可以基于同一套 UI 语言沟通（设计稿中的"卡片"直接对应代码中的 `Card` 组件），大幅减少沟通误差。

- 两者结合使项目结构清晰、可维护性高、利于团队协作。
  - **设计实现**：在一个实际项目中，模块化和组件化是互补而非替代关系。组件关注"用户看到了什么"，模块关注"数据怎么流转"。例如，一个"购物车"组件负责渲染购物车 UI，而一个"购物车状态管理"模块负责维护购物车数据的增删改查。组件调用模块的接口获取数据和执行操作，模块不关心数据最终如何渲染。这种分层架构使得 UI 框架可以替换（从 Vue 换到 React）而业务模块保持不变，也使得多个开发者可以并行工作而不冲突。

### 未来演进方向

#### 架构方面

- **MPA vs SPA**：多页应用 (MPA) 每个页面独立加载，SEO 友好；单页应用 (SPA) 用户体验流畅，但首屏加载慢。
  - **设计思路**：MPA 遵循 Web 的原始模型——每个 URL 对应一个完整的 HTML 页面，页面跳转时浏览器完全刷新。SPA 则改变了这一范式——仅加载一个 HTML 壳，所有页面切换通过 JavaScript 动态替换 DOM 内容实现。两种模型的取舍本质上是"首屏性能 + SEO"与"交互流畅度"的权衡。
  - **设计目的**：理解 MPA 与 SPA 的架构差异，能帮助开发者在项目启动阶段做出正确的技术选型。内容型网站（新闻、博客、电商）更适合 MPA 或 SSR（SEO 是核心需求）；工具型应用（后台管理、在线编辑器、数据分析平台）更适合 SPA（交互丰富，SEO 不重要）。

- **SSR** (Server-Side Rendering)：SPA 首屏效率不高时，服务端渲染兼顾首屏速度和 SEO。
  - **设计实现**：SSR 的核心思想是"同构渲染"——同一套组件代码可以在服务端（Node.js）渲染为 HTML 字符串发送给浏览器，也可以在客户端接管后继续作为 SPA 运行（这个过程称为 Hydration）。Next.js（React）和 Nuxt.js（Vue）是目前最主流的 SSR 框架，它们通过在框架层面处理服务端/客户端差异，让开发者可以用接近纯 SPA 的开发体验获得 SSR 的性能优势。
  - **设计目的**：SSR 解决了 SPA 的两大痛点——首屏白屏时间长（因为要先下载 JS Bundle 再渲染）和 SEO 差（搜索引擎爬虫可能不执行 JavaScript）。但 SSR 也引入了新的复杂性：服务端需要 Node.js 环境、需要考虑服务端与客户端的状态同步、需要处理仅在浏览器端可用的 API（如 `window`、`localStorage`）。SSR 是"按需采用"的方案，不应作为所有项目的默认选择。

#### 技术方面

- 渲染方法：从 **MVVM** (Model-View-ViewModel) 到**双向绑定** (Two-way Data Binding)。
  - **设计思路**：MVVM 将 UI 开发分为三层——Model（数据模型）、View（视图模板）、ViewModel（视图模型，连接 Model 和 View）。ViewModel 通过数据绑定机制使 View 自动反映 Model 的变化，无需手动操作 DOM。双向绑定是数据绑定的强化——Model 变化自动更新 View，View 的用户输入也自动更新 Model，消除了"数据流向"的手动管理。
  - **设计目的**：MVVM 从根本上改变了前端开发的心智模型——从"命令式 DOM 操作"转向"声明式数据绑定"。开发者不再需要编写 `document.getElementById('price').textContent = data.price` 这样的代码，而是直接在模板中声明 `{{price}}`，框架自动处理 DOM 更新。这使得代码量大幅减少、bug 率降低、可维护性提升。

- **SPA 路由问题**：前端路由 (Hash / History API) 实现页面无刷新切换。
  - **设计实现**：Hash 路由利用 URL 的 `#` 片段（hash），hash 的变化不会触发页面刷新，通过监听 `hashchange` 事件感知路由变化。History 路由利用 HTML5 History API 的 `pushState` 和 `replaceState` 方法修改 URL 而不刷新页面，配合 `popstate` 事件感知浏览器前进/后退操作。History 路由的 URL 更美观（没有 `#` 符号），但需要服务端配置回退规则（所有路径返回同一个 HTML）。
  - **设计目的**：SPA 路由解决了"单页面内部视图切换"与"浏览器地址栏 URL"的同步问题。没有前端路由，SPA 中的页面切换无法通过浏览器前进/后退按钮导航，也无法通过 URL 直接访问特定视图（不利于分享和书签），用户体验会严重退化。

- **数据状态保持**：SPA 中跨组件的状态管理（Vuex/Redux 等）。
  - **设计思路**：SPA 的组件树结构带来了"跨组件通信"的难题——兄弟组件之间没有直接的引用关系，父子组件通过 props 和 events 通信，但这种逐层传递在深层嵌套时会变得异常繁琐（称为"Prop Drilling"）。状态管理库将共享状态提升到组件树之外，所有组件都可以直接读取和修改全局状态，无需通过中间组件转发。
  - **设计实现**：Redux 采用"单一 Store + 纯函数 Reducer + Action 驱动"的架构，强调数据流的单向性和可预测性。Vuex 采用类似理念但语法上更贴近 Vue 的响应式系统。两者的核心原则相同：状态是可预测的（只能通过显式的 Action/Commit 修改）、状态是可追踪的（DevTools 记录每一次状态变更）、状态与视图是解耦的（组件不直接修改状态，而是派发意图）。
  - **设计目的**：状态管理不是为了复杂而复杂——当项目跨越 20+ 个页面、100+ 个组件时，缺乏统一的状态管理会导致"数据从哪里来、到哪里去"完全不可追踪。状态管理库将应用的数据流从"分布式的混乱"变为"集中式的有序"，使大型 SPA 在长期维护中保持可控。

## 八、本章小结

本章核心三部分：

1. **异步请求**：Promise 对象 + Fetch API + Axios 库。
   - **设计主线**：从"回调方案的问题"出发，引出 Promise 作为解决方案（状态机 + 链式调用），再到 Fetch（原生实现）和 Axios（第三方增强）作为 Promise 在 HTTP 场景的具体应用。这条主线贯穿了异步编程从"能用"到"好用"再到"工程化"的演进路径。理解这一演进，不仅是为了通过考试，更是为了在面对实际项目中不同的异步场景时，能做出有依据的技术选型。

2. **前后对比**：Fetch（原生）与 Axios（第三方库）的优劣分析，async/await 语法糖。
   - **设计主线**：对比的目的不是评判谁"更好"，而是明确各自适用的场景——Fetch 适合轻量级项目和对零依赖有要求的场景；Axios 适合需要拦截器、超时控制、广泛兼容性的企业级项目。async/await 作为 Promise 的语法糖，统一了二者的使用体验，让开发者在选择底层 HTTP 库时拥有更大的灵活性。

3. **项目工程化**：功能拆解 -> 资源打包 -> 模块化与组件化，未来向 SPA / SSR / MVVM 方向演进。
   - **设计主线**：这一部分从前端的"微观技术"（Promise、Fetch、Axios）上升到"宏观架构"（工程化、模块化、组件化、应用架构），揭示了前端开发从"写脚本"到"做工程"的范式转变。一个成熟的前端开发者不仅需要掌握具体 API，更需要理解这些 API 在整体架构中的位置和价值——就像建筑工人需要知道每块砖在整栋楼中的位置一样。

## 状态转换图


```
new Promise()
    |
    v
pending (进行中)
   / \
  /   \
resolve()  reject()
  |         |
  v         v
fulfilled  rejected
  \        /
   \      /
    v    v
resolved (已定型)
    |
    v
.then() / .catch() 回调执行
```


- **设计要点**：理解状态转换图是理解 Promise 全部行为的钥匙。图中最关键的两条规则是：(1) 状态只能从 `pending` 出发，到达 `fulfilled` 或 `rejected` 后不可再变；(2) `resolved`（已定型）是 `fulfilled` 和 `rejected` 的上位概念，表示"已经结束了，无论成功还是失败"。一旦理解了这两条规则，就能自行推导出 Promise 在各种场景下的行为——链式调用的值传递、错误冒泡、多次 `.then()` 的行为等。

## Fetch vs Axios 决策速览

| 特性 | Fetch | Axios |
|------|-------------|--------------|
| 来源 | 原生 ES6 | 第三方库 |
| JSON 处理 | 手动 `.json()` | 自动转换 |
| 错误处理 | 仅网络错误 reject | HTTP 错误自动 `.catch` |
| 请求取消 | AbortController | CancelToken / AbortController |
| 拦截器 | 无 | 有（请求/响应） |
| 超时设置 | 无原生支持 | 内置 `timeout` |
| 兼容性 | 不支持 IE | 更友好 |
| 体积 | 原生（0 依赖） | 需要额外引入 |

- **决策建议**：如果项目需要支持 IE、需要请求/响应拦截器（如统一添加 Token 和错误处理）、或需要内置超时控制，优先选择 Axios。如果项目是轻量级的演示/原型、对包体积敏感（如移动端 H5）、或只需要简单的 GET/POST 请求且目标浏览器均为现代浏览器，优先选择 Fetch。如果两者难以取舍，注意 Axios 的体积约 14KB (gzip 后约 5KB)，对绝大多数项目来说这一体积增加是可以接受的。

---

> 复习建议：结合教材中的代码范例进行动手练习；理解状态转换机制和链式调用原理；能写出 fetch 和 axios 的基本请求代码。考试时常出现"根据代码片段判断输出顺序"的题目，这考察的是对 Event Loop、微任务队列、Promise 状态转换时机的综合理解。"根据场景选择 HTTP 方案"是简答题的常见题型，需要能从"体积、兼容性、错误处理、拦截器需求"等维度进行分析和阐述。

## 客观考点总结

### 一、选择题 / 填空题考点

1. **Promise 的三种状态**：`pending`（进行中）、`fulfilled`（已成功）、`rejected`（已失败）。初始状态为 `pending`，状态只能从 `pending` 转变为 `fulfilled` 或 `rejected`，一旦改变就凝固不可再变。
2. **Promise 内部属性**：`PromiseState`（保存状态）和 `PromiseResult`（保存结果值）。这两个属性对外部代码不可直接访问。
3. **Promise 状态转换方向**：`pending` -> `fulfilled`，或 `pending` -> `rejected`。不存在 `fulfilled` -> `rejected` 或反向转换。
4. **`resolved`（已定型）** 的含义：Promise 状态不再是 `pending`，无论结果是 `fulfilled` 还是 `rejected`。
5. **`.then()` 的返回值**：返回一个新的 Promise 对象，这是链式调用的基础。
6. **`.catch()` 的等价写法**：`.then(null, onRejected)`。
7. **`async` 函数的返回值**：始终返回一个 Promise 对象。即使内部 `return` 一个普通值，也会被自动包装为 `Promise.resolve(值)`。
8. **`await` 的使用限制**：只能用于 `async` 声明的异步函数内部。
9. **`fetch()` 的返回值**：返回一个被 Promise 包装的 Response 对象。
10. **`Response.ok`**：布尔值，HTTP 状态码为 2xx 时为 `true`，其他为 `false`。
11. **Fetch 的错误处理特点**：只对网络错误 reject，HTTP 错误码（404、500 等）不会自动进入 `.catch()`，需手动检查 `response.ok`。
12. **Axios 的错误处理特点**：HTTP 错误码（非 2xx）会自动进入 `.catch()`，这是与 Fetch 的重要区别。
13. **模块化 vs 组件化**：模块化按"功能"划分（关注代码组织和复用），组件化按"UI 单元"划分（关注界面封装和复用），一个组件通常包含 HTML + CSS + JS。
14. **外部模块化 vs 内部模块化**：外部模块化引入第三方包（通过 NPM），内部模块化是工程内部按职责拆分文件。
15. **`Promise.all()` 的行为**：全部 Promise 成功则返回结果数组；任一失败则整体 rejected（Fail-fast 模式）。
16. **Response body 的读取特性**：底层基于 Stream 流，只能读取一次；若需多次读取，需使用 `Response.clone()` 创建副本。

### 二、简答题考点

1. **简述 Promise 解决回调地狱的原理**：回调地狱的根本问题是嵌套回调导致代码横向膨胀、错误处理分散、流程控制困难。Promise 通过三个方面解决：(1) 状态凝固——Promise 状态一旦从 pending 变为 fulfilled/rejected 后就永久不变，保证回调只会被正确调用一次；(2) 链式调用——`.then()` 返回新 Promise，将嵌套结构变为扁平链式结构；(3) 统一错误处理——链末端的 `.catch()` 可捕获链上任何一步的错误。

2. **对比 Fetch API 与 Axios 的优缺点，并给出选型建议**：Fetch 优点为零依赖、原生支持、流式处理；缺点为不自动处理 JSON、HTTP 错误不自动 reject、无拦截器。Axios 优点为自动 JSON 转换、HTTP 错误自动 reject、支持拦截器、内置超时和请求取消；缺点为额外依赖增加体积。选型建议：轻量级项目/原型开发优先 Fetch；企业级项目/需要拦截器/需要兼容旧浏览器优先 Axios。

3. **简述 `async/await` 与 Promise 的关系以及 `async/await` 的优缺点**：`async/await` 是 Promise 的语法糖，底层机制完全相同。`async` 函数始终返回 Promise，`await` 等待 Promise 结果。优点：用同步风格编写异步代码，可读性大幅提升，错误处理可用原生 `try-catch`，与条件/循环语句自然结合。缺点：`await` 默认串行执行，容易无意中造成不必要的等待；reject 异常需手动 `try-catch` 捕获，否则会变成未处理的 Promise rejection。

4. **简述前端项目工程化的演进路径**：第一步——JavaScript 功能拆解：将整体业务逻辑拆分为独立功能模块，理清模块间依赖关系。第二步——静态资源打包：使用 Webpack/Vite 等构建工具合并文件、压缩体积、语法转换(Babel)、优化加载性能。第三步——模块化与组件化：模块化按功能划分代码组织，组件化按 UI 单元封装复用，两者结合实现高内聚低耦合的项目结构。未来向 SPA/SSR/MVVM 方向持续演进。

5. **解释 Promise 的"状态凝固"特性及其意义**：Promise 状态只能从 pending 变为 fulfilled 或 rejected，一旦改变就永久不变。这一特性的意义在于：(1) 消除回调被多次调用的隐患——resolve/reject 被多次调用时只有第一次生效；(2) 使 Promise 可以缓存结果——已定型的 Promise 在任何时候添加 `.then()` 都能立即获取结果；(3) 提供了可靠的异步流程控制基础——后续的链式调用无需担心状态意外变化。

6. **解释 `fetch()` 中为什么要手动检查 `response.ok`**：Fetch 设计遵循"HTTP 错误也是有效响应"的哲学——从网络层面看，服务器返回 404 或 500 是成功的 HTTP 通信（请求已到达服务器并收到响应），因此 Fetch 不会对这类状态码自动 reject。只有网络层面的错误（DNS 解析失败、连接超时、CORS 错误等）才会导致 reject。因此开发者需要通过 `response.ok`（或 `response.status`）手动判断 HTTP 状态码是否表示业务逻辑上的成功。

7. **解释 Axios 拦截器的设计原理和应用场景**：拦截器采用"中间件管道"（Middleware Pipeline）模式，分为请求拦截器和响应拦截器。请求拦截器按注册顺序正序执行（先注册的先执行），响应拦截器按反序执行（后注册的先执行）。应用场景包括：统一为每个请求添加认证 Token；全局 Loading 动画的控制（请求开始时显示，响应后隐藏）；统一错误处理（如 401 时自动跳转登录页）；请求/响应日志记录；敏感数据加密/脱敏等。

### 三、易混淆概念

1. **异步 (Asynchronous) vs 并发 (Concurrency)**：异步是"不等待结果，先做别的事"，是一种编程模型；并发是"多个任务同时推进"，是一种执行模型。JavaScript 是"单线程 + 异步"——同一时刻只执行一段代码，但通过事件循环可以在多个任务之间切换。Promise 解决的是异步流程的组织问题，不是并发问题。

2. **`Promise.all()` vs `Promise.allSettled()`**：`Promise.all()` 采用 Fail-fast 策略——任一子 Promise reject 则整体立即 reject，适合"全部成功才有意义"的场景。`Promise.allSettled()` 会等待所有子 Promise 完成（无论成功或失败），返回每个 Promise 的结果对象（含 `status` 和 `value`/`reason`），适合"需要知道每个任务的独立结果"的场景。

3. **`resolved`（已定型）vs `fulfilled`（已成功）**：`resolved` 是上位概念，表示 Promise 的状态不再是 `pending`，包括 `fulfilled` 和 `rejected` 两种情况。`fulfilled` 特指操作成功完成。一个 `rejected` 的 Promise 也是 `resolved` 的。

4. **`try-catch` vs `.catch()`**：两者都是错误处理机制，但适用范围不同。`try-catch` 用于同步代码和 `async/await` 中捕获 `await` 表达式的 rejection。`.catch()` 用于 Promise 链中捕获 rejection。在 `async` 函数内部，`try-catch` 可以捕获 `await` 的 rejection，等价于在对应的 Promise 上调用 `.catch()`。两者不能互相替代——`try-catch` 无法捕获直接在 Promise 链上（未使用 `await`）的 rejection。

5. **模块化 (Modularization) vs 组件化 (Componentization)**：模块化按"功能职责"划分，关注点是"代码如何组织"，一个模块通常是一个 JS 文件。组件化按"UI 单元"划分，关注点是"界面如何封装复用"，一个组件包含 HTML + CSS + JS。两者是正交概念——一个组件可能使用多个模块，一个模块可能被多个组件引用。实际项目中两者共存互补。

6. **Fetch 的"不自动 reject HTTP 错误" vs Axios 的"自动 reject HTTP 错误"**：这是两者最核心的行为差异。Fetch 认为 HTTP 404/500 是正常的 HTTP 响应（网络通信成功），只有网络错误才 reject，因此需要手动 `response.ok` 判断。Axios 认为任何非 2xx 状态码都是错误，自动 reject 进入 `.catch()`。两种设计各有道理，Fetch 更贴近 HTTP 协议本身的语义，Axios 更贴近业务开发的直觉。

7. **`XMLHttpRequest` (XHR) vs Fetch API**：XHR 是基于事件（`onreadystatechange`、`onload`）的旧方案，API 笨重（需要手动检查 `readyState`）。Fetch 是基于 Promise 的现代化方案，语法简洁，但缺少 XHR 原生的上传/下载进度事件（`xhr.upload.onprogress`），需要借助 Streams API 实现类似功能。Fetch 不支持请求超时设置，需配合 `AbortController` 的 `timeout` 信号或 `Promise.race()` 模拟。

8. **事件 (Event) vs Promise**：事件可以多次触发（如 `click` 事件），Promise 只决议一次；事件错过触发时机就无法获取历史值，Promise 定型后随时调用 `.then()` 都能获取结果；事件通过 `addEventListener`/`removeEventListener` 管理监听器，Promise 通过 `.then()` 注册回调并自动管理生命周期。
