## Vue 简介 (Introduction)

### 由来 (Origin)

- 作者：尤雨溪 (Evan You)，2014 年创建
> **设计思路**：Evan You 在 Google 使用 AngularJS 工作期间，深刻体会到 AngularJS 的 ViewModel 层在管理数据与视图同步方面非常有价值，但整个框架过于庞大。他想要一个仅聚焦于视图层、同时保留响应式数据绑定能力的轻量方案。**设计实现**：Vue 从 AngularJS 中提取了 MVVM 模式的核心——ViewModel——并将其封装为一个独立的、不依赖任何框架的 JavaScript 库，最小化 API 表面积。**设计目的**：提供一种比 AngularJS 更轻量、比直接操作 DOM 更优雅的视图层解决方案，让开发者能以声明式方式构建 UI，而不必引入完整的前端 MVC 架构约束。

- 从 AngularJS 中提取核心功能 (ViewModel)，打造更轻量、更灵活的框架
> **设计思路**：AngularJS 的脏检查 (dirty checking) 机制性能开销大，且全框架的 MVC 设计使简单项目也必须引入大量概念和模板代码。**设计实现**：Vue 保留了双向数据绑定和指令 (directives) 的核心理念，但用基于 Getter/Setter（Vue 2）和 Proxy（Vue 3）的响应式系统替代脏检查，极大降低了运行时开销。**设计目的**：创建一个核心库体积小（gzip 后约 20KB）、运行高效的视图层框架，让小型项目也能享受响应式编程带来的开发效率提升。

- 定位：用于构建用户界面的**渐进式 JavaScript 框架** (Progressive JavaScript Framework)
> **设计思路**：真实项目中，需求复杂度的差异极大——一个简单的表单增强和一个完整 SPA 所需的技术栈完全不同。**设计实现**：Vue 的核心库只包含视图层渲染和响应式系统，而 Vue Router（路由）、Pinia（状态管理）、Vue CLI / Vite（构建工具）等作为官方配套库，按需引入。**设计目的**：让 Vue 既可以作为一个轻量的页面增强库被引入（替代 jQuery 的 DOM 操作），也可以作为完整的前端框架支持大型单页应用开发，实现"增量式采用"。

- 官网：`https://cn.vuejs.org`
> 官方中文文档质量高，社区活跃，是中国开发者学习 Vue 的首选渠道。

### 核心特性 (Core Features)

- **渐进式** (Progressive)：从简单到复杂逐步引入，降低学习门槛，适合各种规模项目
> **设计思路**：前端框架的传统困境是"全有或全无"——要么完全接受框架的全部约束，要么完全不用。Vue 的设计打破了这个困境。**设计实现**：通过分层架构，Vue 核心仅处理模板编译和响应式数据绑定，路由、状态管理、SSR 等高级功能通过独立包提供。开发者可以从一个 `<script>` 标签引入起步，逐步升级到完整 SPA 架构。**设计目的**：最大程度降低技术选型的风险和团队学习成本，让 Vue 能适应从传统多页应用 (MPA) 改造到全新 SPA 项目的各种场景。

- **响应式** (Reactive)：数据变化自动更新视图，避免手动 DOM 操作
> **设计思路**：在传统的 jQuery 式开发中，开发者需要手动追踪哪些 DOM 节点依赖哪些数据，当数据变化时编写大量 `.innerHTML`、`.text()` 等命令式更新代码。这种模式极易产生数据与视图不同步的 Bug。**设计实现**：Vue 通过 Proxy 拦截所有对数据对象的访问，在组件渲染期间自动收集依赖（哪些数据被哪些组件使用），数据变更时自动通知对应组件重新渲染。**设计目的**：将状态到视图的映射从命令式转变为声明式，使得 UI 开发模式从"我应该如何修改 DOM"转变为"这个状态对应的 UI 应该长什么样"。

- **组件化** (Component-based)：将 UI 拆分为独立、可复用的组件，提高代码复用性
> **设计思路**：复杂用户界面的核心挑战在于管理复杂度——一个数千行的模板文件几乎无法维护。组件化将大问题拆分为小问题，每个组件只关注一个功能块。**设计实现**：Vue 的单文件组件 (.vue) 将 `<template>`（结构）、`<script>`（逻辑）和 `<style>`（样式）封装在同一个文件中，通过 Props 接收外部数据，通过 Emit 对外发送事件，形成明确的数据单向流动边界。**设计目的**：建立清晰的组件树结构，实现关注点分离和高内聚低耦合的软件架构，使大型应用能以乐高式拼接方式构建。

- **模板语法** (Template Syntax)：基于 HTML 的模板，易学易用，降低学习成本
> **设计思路**：React 的 JSX 虽然灵活（本质上是 JavaScript 表达式），但对习惯 HTML/CSS 的页面开发者和设计师存在一定的学习门槛。Vue 选择了更接近传统 Web 开发习惯的模板方案。**设计实现**：Vue 模板是合法的 HTML，通过指令 (如 `v-if`、`v-for`、`v-bind`) 扩展 HTML 的语义。模板在编译阶段被转换为渲染函数 (render function)，运行时直接执行高效的虚拟 DOM 更新。**设计目的**：让具备 HTML/CSS 基础知识的开发者几乎零成本上手，同时模板的静态分析特性也为编译时优化（如静态提升、预字符串化）提供了空间。

- **双向绑定** (Two-way Binding)：v-model 实现数据双向同步，简化表单处理
> **设计思路**：表单是 Web 应用中最常见的交互元素，传统的表单处理需要分别监听 input 事件（更新数据）和绑定 value 属性（响应数据变化），代码重复且易出错。**设计实现**：`v-model` 本质上是一个语法糖——对于文本 `<input>`，它展开为 `v-bind:value` + `v-on:input`；对于其他表单控件（checkbox、radio、select），它会智能选择对应的属性和事件。**设计目的**：将数据模型与表单视图的同步逻辑自动化，减少样板代码，让开发者专注于业务逻辑而非 DOM 事件处理。

### Vue 与 React 对比 (Comparison)

| 维度 | Vue | React |
|------|-----|-------|
| 模板语法 | HTML-based 模板 | JSX |
| 响应式 | 基于 Proxy 的响应式系统 | 基于 setState 的状态更新 |
| 数据绑定 | 双向绑定 (v-model) | 单向数据流 |
| 学习曲线 | 平缓，渐进式 | 中等，需学习 JSX |
| 生态系统 | Vue Router、Pinia、Vue CLI | React Router、Redux、CRA |
| 灵活性 | 中等 | 高，更接近原生 JS |

> **架构视角**：Vue 和 React 代表了两种不同的框架哲学。Vue 强调"开发者的便利性"，通过模板和响应式系统自动化了许多底层操作（依赖追踪、DOM 更新），开发者只需声明数据与视图的关系；React 强调"显式性和可预测性"，通过单向数据流和显式的 setState，让应用在任何时刻的状态都可追溯。两种哲学没有绝对优劣之分：Vue 更适合追求开发效率和低学习成本的团队，React 更适合需要高度灵活性和精细控制的复杂应用。

## Vue 模板语法 (Template Syntax)

### 基于 HTML 的模板

- Vue 使用基于 HTML 的模板语法，相比 JSX 更直观，更接近传统 HTML，学习成本更低
> **设计思路**：模板和 JSX 的分歧本质上是"声明式语法 vs 命令式语法"的选择。Vue 认为 UI 结构应该用类 HTML 的声明式语法描述，因为 HTML 本身就是描述页面结构的领域特定语言 (DSL)，用它来描述 UI 是最自然的选择。**设计实现**：Vue 的模板编译器负责将模板解析为 AST（抽象语法树），再转换为渲染函数（render functions）。这个过程发生在构建阶段（使用 SFC 时）或运行时（使用浏览器内模板时），最终产出的渲染函数与 React 的 render 函数在原理上相同——都用虚拟 DOM 描述 UI。**设计目的**：保持 HTML 表达力的同时，通过编译步骤获得与 JSX 等价的运行时性能，并在编译阶段进行静态分析以实现编译时优化（如静态节点提升、补丁标记）。

### 指令系统 (Directive System)

| 指令 | 作用 | 示例 |
|------|------|------|
| `v-text` | 纯文本绑定 | `<span v-text="message"></span>` |
| `v-html` | HTML 内容绑定 | `<div v-html="htmlContent"></div>` |
| `v-bind` | 属性绑定 | `<img v-bind:src="imageUrl" />` |
| `v-on` | 事件绑定 | `<button v-on:click="handleClick">` |
| `v-model` | 双向绑定 | `<input v-model="username" />` |
| `v-if` | 条件渲染 | `<div v-if="show">显示</div>` |
| `v-for` | 列表渲染 | `<li v-for="item in list">{{ item }}</li>` |
| `v-show` | 条件显示 | `<div v-show="visible">可见</div>` |

> **设计思路**：指令系统是 Vue 模板语法的核心。传统 HTML 只能描述静态结构，无法表达"这个元素是否应该存在"或"这个属性值是什么"这类动态语义。Vue 通过指令扩展 HTML 的语义，使得开发者可以在 HTML 中直接声明动态行为——本质上是在 HTML 属性上添加了编程语言能力。**设计实现**：每个指令在模板编译阶段被转换为特定的渲染逻辑。例如 `v-if` 在编译为渲染函数时变成三元表达式或条件判断；`v-for` 变成数组的 `map()` 调用。指令的前缀 `v-` 作为命名空间确保了它们不会与标准 HTML 属性冲突。**设计目的**：在不发明新模板语言的前提下，为 HTML 注入动态能力，保留 HTML 语法的直观性同时实现完整的视图层抽象。

### v-if 与 v-show 对比

| 场景 | v-if | v-show |
|------|------|--------|
| 条件频繁切换 | 不推荐 | **推荐** |
| 条件很少改变 | **推荐** | 不推荐 |
| 需要销毁子组件 | **推荐** | 不适用 |

原理：

- `v-if`：真正的条件渲染，切换时销毁/重建 DOM 元素
> **设计思路**：`v-if` 遵循"条件为假时，元素不应该存在于 DOM 中"的直观语义。这种方式彻底——元素连同其绑定的事件监听器、子组件实例全部被销毁和重建。**设计实现**：在编译阶段，`v-if` 被转换为条件分支语句。当条件为 false 时，虚拟 DOM 中不会包含该节点，diff 算法发现节点缺失后会执行 DOM 移除操作，触发组件的 `onBeforeUnmount` / `onUnmounted` 生命周期。条件重新变为 true 时，节点被完整重建，经历 `onBeforeMount` / `onMounted`。**设计目的**：适用于根据用户状态或权限决定是否展示完整功能区域（如管理员面板、登录后内容），因为条件为假时该区域的所有资源（内存、事件监听）都得到释放。

- `v-show`：始终渲染，仅切换 CSS `display` 属性
> **设计思路**：`v-show` 的设计理念是"始终存在于 DOM 中，但可能不可见"。这在需要频繁切换可见性的场景中有显著优势，因为避免了 DOM 节点的销毁与重建的开销。**设计实现**：元素始终被渲染并保留在 DOM 中，`v-show` 简单地切换元素的 `display` CSS 属性（`none` / 默认值）。由于元素一直存在，其内部状态、绑定的数据和事件监听器也一直保持，不会丢失。**设计目的**：适用于频繁切换的可折叠面板、Tab 切换、模态框等场景，避免销毁重建带来的性能开销和状态丢失问题。

## Vue 组件与数据传递 (Components & Data Flow)

### 组件 (Components)

- 组件是 Vue 应用的基本构建块，将 HTML、CSS、JavaScript 封装在一起，实现可复用的 UI 单元
> **设计思路**：组件化的核心理念是"关注点分离"——不是按文件类型分离（HTML、CSS、JS 各一个文件），而是按功能块分离。Vue 的单文件组件将同一个功能块的模板、逻辑和样式放在一起，使得修改一个功能时不需要跨文件查找。**设计实现**：每个 `.vue` 文件经过 Vue 编译器处理后，模板被编译为渲染函数，`<script>` 导出组件选项对象（Options API）或组合函数（Composition API），`<style>` 被打包到作用域样式表中。三者被整合为一个组件定义，由 Vue 运行时实例化为组件实例。**设计目的**：以功能为中心组织代码，让每个组件的内部实现高度内聚，对外暴露清晰的 Props 和 Events 接口，形成松耦合的组件化架构。

- Vue 采用**单文件组件** (.vue 文件, Single File Components)
> **设计思路**：SFC 是 Vue 在设计上的一大创新。它解决了传统开发中"一个功能模块的代码分散在不同类型文件中的碎片化问题"——修改一个按钮组件可能需要打开 `.html`、`.css`、`.js` 三个文件。**设计实现**：SFC 需要构建工具支持（如 Vite、webpack 的 `vue-loader`），在构建阶段编译为标准的 JavaScript 模块。每个 SFC 编译后产出一个包含 render 函数、生命周期注册和样式注入逻辑的对象。**设计目的**：提升开发者体验——在同一文件中看到组件的完整面貌，减少上下文切换，同时让构建工具能够进行更精细的静态分析和优化。

**.vue 文件成员：**

| 成员 | 作用 |
|------|------|
| `<template>` | HTML 结构，只能有一个根元素 |
| `<script>` | JavaScript 逻辑，`setup` 是组合式 API (Composition API) |
| `<style>` | 样式，`scoped` 表示样式只作用于当前组件 |

> **设计要点**：`<template>` 要求单一根元素是因为 Vue 的虚拟 DOM diff 算法需要返回单个 VNode。从 Vue 3 Fragment 开始允许多根节点。`<script setup>` 是 Vue 3 引入的编译时语法糖，在编译阶段将其中顶层变量自动暴露给模板（无需显式 return），减少了样板代码。`<style scoped>` 通过为元素添加唯一属性选择器（如 `data-v-xxxxx`）实现样式隔离，避免了全局样式污染问题。

### 父组件传子组件：Props

- 父组件通过 `props` 对象向子组件传递数据
> **设计思路**：在组件树中，数据自然地从上向下流动。Props 是父组件向子组件传递数据的唯一标准通道，保证了数据流的单向性和可追溯性——任何组件的状态变化都可以通过追踪 Props 的来源定位。**设计实现**：在父组件模板中，通过在子组件标签上使用 `v-bind` 或直接绑定属性值，Vue 在创建子组件实例时将这些值注入到子组件的 `props` 中。Props 在子组件中是只读的（不可修改），确保了数据流动的不可逆性。**设计目的**：建立清晰的数据流向约定，使组件树的数据来源可追溯、状态变化可预测，这在复杂应用中对于调试和维护至关重要。

**Props 配置选项：**

| 选项 | 说明 |
|------|------|
| `type` | 指定类型：String, Number, Boolean, Array, Object, Function |
| `required` | 是否必填 (Boolean) |
| `default` | 默认值 |
| `validator` | 自定义验证函数 |

> **设计思路**：Props 配置不仅仅是类型声明，更是一份"组件的契约文档"。通过声明 type、required、default 和 validator，子组件清晰地定义了自己的 API 接口，调用方可以准确知道需要传入什么。**设计实现**：在开发模式下，Vue 会对传入的 Props 进行运行时验证——类型匹配、必填检查、自定义验证函数执行。验证失败会在控制台输出警告，帮助开发者快速定位问题。**设计目的**：Props 配置相当于函数签名中的参数定义和类型注解，让组件之间的契约明确且可执行（通过运行时检查），避免"传错参数"导致的隐性 Bug。

### 子组件传父组件：Emit 事件

- 子组件通过 `emit` 事件向父组件传递数据
> **设计思路**：子组件不能直接修改 Props（数据单向向下），但子组件的内部交互（按钮点击、表单输入）需要通知父组件更新状态。Emit 事件提供了一个"向上通知"的机制，父组件监听事件并决定如何响应。**设计实现**：子组件使用 `defineEmits` 声明可触发的事件名，然后调用 `emit('event-name', payload)` 触发事件。父组件在模板中使用 `v-on:event-name` 或 `@event-name` 监听，Vue 运行时在组件的事件系统中建立监听关系，当 emit 被调用时查找对应的父组件监听函数并执行。**设计目的**：保持单向数据流的一致性——数据始终向下传递（通过 Props），状态更新始终向上通知（通过 Emit）。这种单向循环确保了数据流向的清晰性和状态变化的可控性。

- 子组件触发自定义事件，父组件监听并响应
> **设计思路**：Emit 机制来源于设计模式中的"观察者模式"（Observer Pattern），子组件不关心谁来监听，只负责发出通知；父组件决定如何响应。这种解耦让子组件可以在不同上下文中复用，因为它的行为不依赖于特定的父组件实现。

## Vue 响应式系统 (Reactive System)

### 响应式原理 (Reactivity Principle)

- Vue 的响应式系统是核心特性之一：当数据变化时，视图会自动更新
> **设计思路**：前端开发最核心、也最易出错的环节就是"数据与视图的同步"。在传统的命令式开发中，每一个可能导致数据变化的操作（网络响应、用户输入、定时器）之后，都需要手动调用 DOM 更新代码。Vue 的响应式系统将这个过程完全自动化，开发者只需关注"数据是什么"，而非"如何把数据放进 DOM"。**设计实现**：响应式系统的依赖链路为：Proxy 拦截数据读写 -> 渲染函数执行时收集依赖（建立 data -> component 的映射） -> 数据修改时触发 setter -> 通知所有依赖该数据的组件 -> 组件重新渲染生成新的虚拟 DOM -> diff 算法计算最小变更 -> 更新真实 DOM。**设计目的**：将 UI 开发从"状态同步"的繁琐工作中解放出来，使代码回归到业务逻辑本身，大幅减少因手动 DOM 操作失误导致的 Bug。

- **Vue 3 使用 Proxy** 对象拦截数据的读取和写入
> **设计思路**：Vue 2 使用 `Object.defineProperty` 实现响应式，但该方法存在两个严重局限：无法检测对象属性的添加/删除，以及无法处理数组索引赋值和 length 修改。ES6 引入的 Proxy 可以代理整个对象的所有操作，从根本上解决了这些问题。**设计实现**：Proxy 构造函数创建一个目标对象的代理，可以拦截 13 种基本操作，包括 get、set、deleteProperty、has、ownKeys 等。Vue 3 的 `reactive()` 函数内部将目标对象替换为 Proxy 代理，所有对该对象的操作都先经过拦截器，从而实现完全的变更追踪。**设计目的**：提供完整的、无死角的响应式数据追踪能力，让开发者可以在响应式对象上执行任何常规 JavaScript 操作（增删属性、数组操作等），而无需学习特殊的 API（Vue 2 中需要使用 `Vue.set` / `Vue.delete`）。

**工作流程：**

- **依赖收集** (Dependency Tracking)：当数据被读取时，建立依赖关系
> **设计思路**：依赖收集的核心思想是"记住谁在用这个数据"。当组件渲染函数执行时，如果它访问了某个响应式数据，就自动建立一条"这个数据变了 -> 这个组件需要重新渲染"的依赖链。**设计实现**：实现上依赖一个全局的"当前副作用"追踪变量。当渲染函数执行时，Vue 将它设为当前活跃的副作用 (effect)，Proxy 的 get 拦截器在数据被访问时将当前副作用添加到该数据的依赖集合中。整个过程对开发者完全透明。**设计目的**：实现精细化的更新——只有真正使用了某个数据的组件才会在该数据变化时重新渲染，而非整个应用全部刷新。

- **派发更新** (Dispatch Update)：当数据被修改时，触发视图更新
> **设计思路**：依赖收集解决了"谁依赖我"的问题，派发更新解决了"我变了应该通知谁"的问题。当依赖收集的记录准确时，派发更新就可以做到"只更新该更新的部分"，实现最小化渲染开销。**设计实现**：Proxy 的 set/deleteProperty 拦截器在数据变更时，遍历该数据的所有依赖（收集到的副作用），将它们加入异步更新队列（使用 `nextTick` 机制批处理）。批处理确保了连续多次数据修改只触发一次组件重渲染，避免了不必要的重复计算。**设计目的**：实现高效且精确的视图更新——最小化 DOM 操作次数和范围，达到接近手写优化的性能水平。

**响应式数据声明方式：**

| 方式 | 适用类型 | 说明 |
|------|----------|------|
| `ref()` | 基本类型 (String, Number 等) | 通过 `.value` 访问/修改 |
| `reactive()` | 对象类型 (Object, Array) | 直接访问/修改属性 |

> **设计思路**：Vue 3 提供 `ref()` 和 `reactive()` 两种响应式 API，源于 JavaScript 的语言限制。Proxy 只能代理对象，无法代理原始值（string、number 等基本类型直接按值传递，无法被拦截）。`ref()` 通过将一个基本值包装在对象 `{ value: ... }` 中解决了这个问题。**设计实现**：`ref()` 内部创建一个带有 `.value` 属性的对象，对该对象使用 getter/setter 拦截 `.value` 的访问。在模板中 Vue 自动解包 ref（不需要 `.value`），这是编译器的便利处理。`reactive()` 直接返回整个对象的 Proxy 代理，所有嵌套属性访问自动被追踪。**设计目的**：为不同类型的数据提供一致且合适的响应式方案，同时在模板中保持简洁的使用体验。

### 计算属性 (Computed Properties)

- 计算属性是基于依赖自动计算的值，具有**缓存特性**
> **设计思路**：在模板中直接写复杂的表达式会导致模板臃肿且难以维护。如果使用 methods 处理，每次重新渲染都会重新计算，即使原始数据没有变化。计算属性解决了这一矛盾——既可以在模板中简洁使用，又具有缓存能力。**设计实现**：计算属性内部创建一个 `ComputedRefImpl` 实例，其中维护一个 dirty 标记。当依赖数据变化时，dirty 被设为 true，下一次读取计算属性时触发重新计算并缓存结果，dirty 重置为 false。如果依赖数据没有变化，多次访问计算属性直接返回缓存值，不触发重新计算。**设计目的**：将"派生状态"的计算逻辑集中管理，同时保证只在实际需要时重新计算，避免不必要的性能开销。

- 只有当依赖数据变化时，计算属性才会重新计算
> **设计思路**：这一特性使得计算属性非常适用于复杂的、开销较大的计算（如数组过滤、排序、聚合），因为如果依赖没有变化，计算开销为零。这是它区别于 methods 的最核心特征。

**computed 与 methods 对比：**

| 对比维度 | `computed` | `methods` |
|----------|------------|-----------|
| 缓存 | 依赖变化时重新计算 | 每次调用都执行 |
| 调用方式 | `{{ fullName }}` | `{{ getFullName() }}` |
| 返回值 | 必须返回值 | 可返回可不返回 |
| 副作用 | 不应该有副作用 | 可以有副作用 |
| 使用场景 | 派生值计算、过滤、格式化 | 事件处理、数据获取、操作执行 |

> **架构选择指南**：计算属性用于"基于现有数据推导出新数据"的场景（纯函数），methods 用于"执行操作"的场景（可能有副作用）。将计算逻辑放在 computed 中，配合缓存特性，可以有效控制渲染性能——在大型列表渲染或复杂计算场景中效果尤为显著。

## 生命周期钩子函数 (Lifecycle Hooks)

| 钩子函数 | 触发时机 | 常用场景 |
|----------|----------|----------|
| `onBeforeMount` | 组件挂载前 | 准备工作 |
| `onMounted` | 组件挂载后 | **数据初始化、DOM 操作** |
| `onBeforeUpdate` | 组件更新前 | 保存状态 |
| `onUpdated` | 组件更新后 | 更新 DOM |
| `onBeforeUnmount` | 组件卸载前 | 确认操作 |
| `onUnmounted` | 组件卸载后 | **清理资源、取消订阅** |

> **设计思路**：生命周期钩子的设计是为了让开发者能够在组件"生命旅程"的关键时间点插入自定义逻辑。Vue 组件的生命周期可以类比为生物的生命过程：创建（mount）、成长（update）、消亡（unmount）。每个阶段的前后都有钩子可供干预。**设计实现**：Vue 运行时在组件实例化过程中维护一个生命周期状态机。当组件进入某个阶段时，按顺序调用注册在该阶段的钩子函数。钩子函数在 Composition API 中以 `onXxx` 的形式使用（必须在 `setup` 同步调用期间注册），在 Options API 中作为组件选项的属性存在。**设计目的**：提供细粒度的组件行为控制能力，使得开发者可以在正确的时机执行初始化（挂载后）、响应变化（更新时）和清理（卸载时）操作，避免内存泄漏和状态错乱。

记忆要点：

- 三对钩子：before/mounted, before/update, before/unmount
> **设计规律**：每对钩子的命名遵循 `onBeforeXxx` / `onXxxed` 模式。"before"钩子在阶段开始前触发（适合做准备工作、保存旧状态），对应的非 before 钩子在阶段完成后触发（适合做后续处理、操作已渲染 DOM）。this 设计使每对钩子角色分明、互补。

- `onMounted` 最常用：数据初始化、发送网络请求、DOM 操作
> **设计原因**：组件只有在挂载到 DOM 后，才能访问真实的 DOM 节点和父组件上下文。因此，任何需要操作 DOM（如初始化图表库、获取元素尺寸）或需要访问完整组件树节点的操作，必须放在 `onMounted` 中执行。网络请求也通常在此发起，因为此时组件已就绪，可以安全地更新数据驱动视图。

- `onUnmounted` 很关键：清理定时器、取消订阅、释放资源
> **设计原因**：单页应用中，组件会频繁地创建和销毁（路由切换、条件渲染等）。如果在组件销毁时没有清理定时器、事件监听器、WebSocket 连接等，这些资源会持续存在（内存泄漏），累积到一定程度会导致页面卡顿甚至崩溃。`onUnmounted` 是防止这类问题的最重要的防线。

## 前端其他知识 (Other Frontend Knowledge)

### TypeScript

- **JavaScript 的痛点**：动态类型语言，缺乏类型检查，大型项目中难以维护
> **设计思路**：JavaScript 的动态类型在小型脚本中提供了灵活性，但在大型应用中，类型不明确导致了两个核心痛点：一是重构困难（修改函数签名后无法自动发现所有调用点），二是代码补全和智能提示不准确（IDE 无法推断变量类型）。**设计实现**：TypeScript 在 JavaScript 之上添加了类型注解和编译时的类型检查系统。开发者为变量、函数参数、返回值添加类型注解，TS 编译器在代码运行前就能发现类型不匹配的错误。**设计目的**：在保持 JavaScript 运行时灵活性的同时，通过静态类型系统提供"编译时安全网"——将类型错误从运行时提前到编码阶段发现，显著降低 Bug 率。

- **TypeScript**：Microsoft 于 2012 年发布，是 JavaScript 的**超集** (Superset)，添加了可选的**静态类型系统** (Static Type System)
> **设计思路**："超集"意味着任何合法的 JavaScript 代码在 TypeScript 中也是合法的。这种设计保证了渐进式迁移的可行性——团队可以首先在 `.js` 文件上获得部分类型推断，然后逐步将文件重命名为 `.ts` 并添加类型注解，实现零中断的迁移。**设计实现**：TS 编译器 (tsc) 负责将 TypeScript 代码编译为纯 JavaScript（去除类型注解），类型检查在编译阶段独立进行，不会影响最终产出的运行时行为。源映射 (source map) 保证了调试时仍能看到原始 TS 代码。**设计目的**：让大型前端项目具备与后端语言（Java、C#）同等级别的类型安全保障，同时不牺牲 JavaScript 生态的兼容性。

- TypeScript 可以与 React 和 Vue 一起使用
> **设计实现**：Vue 3 从底层使用 TypeScript 重写，提供了完整的类型推导。`defineProps`、`defineEmits` 等编译器宏都支持泛型参数。React 通过 `@types/react` 和 `React.FC` 等类型定义提供 TypeScript 支持。两者都能在编译阶段捕获 Props 类型不匹配、事件参数错误等问题。

- 优势：编译时类型检查、更好的 IDE 支持、提升代码可维护性
> **设计目的**：类型系统本质上是"活文档"——类型定义即文档，不存在文档与代码不同步的问题。结合 IDE 的自动补全和重构能力，TypeScript 在降低大型项目维护成本方面的效果已经被行业广泛验证。

### 服务端渲染 (Server-Side Rendering, SSR)

- **为什么需要 SSR**：解决纯客户端渲染 (CSR) 的首屏加载慢、SEO 不友好等问题
> **设计思路**：CSR 的工作流程是"浏览器下载空 HTML -> 下载 JS bundle -> 执行 JS -> 渲染页面"。在这个过程中，用户会看到白屏，且搜索引擎爬虫抓取到的只是空壳 HTML。SSR 将首次渲染移到服务器端完成，浏览器直接收到带内容的 HTML。**设计实现**：SSR 框架在 Node.js 服务端运行 Vue/React 组件，生成完整的 HTML 字符串返回给浏览器。浏览器首先展示这个预渲染的 HTML（用户立即看到内容），然后 JavaScript 进行"注水" (hydration)，将静态 HTML 升级为可交互的 SPA。**设计目的**：在保持 SPA 交互体验的优势的同时，解决其两大天然缺陷——首屏空白时间 (TTFP) 过长和搜索引擎无法索引内容 (SEO)。

- Web 软件系统架构的发展演变：从传统服务端渲染 (MPA)，到客户端渲染 (SPA/CSR)，再到现在的主流方案——服务端渲染 (SSR) 或静态生成 (SSG)
> **架构演变脉络**：传统 MPA 时代（PHP/JSP，每次导航完整刷新） -> 现代 SPA/CSR 时代（React/Vue 接管前端，局部刷新体验佳，但首屏慢、SEO 差） -> 混合/同构时代 (SSR/SSG，首屏服务端渲染，后续交互客户端处理，兼顾性能和搜索引擎)。这种演变是螺旋上升的——SSR 看起来像是回到了 MPA 的服务端渲染，但技术本质完全不同（同构 JS、组件化架构、客户端注水），是在更高层次上的回归。

- SSR 方案：Next.js (React)、Nuxt.js (Vue)
> **设计思路**：SSR 的实现涉及复杂的构建配置、路由劫持、数据预取和状态同步问题，直接手动实现门槛极高。Next.js 和 Nuxt.js 作为元框架 (Meta Framework)，将这些复杂性封装在框架内部。**设计实现**：Nuxt.js 基于 Vue 3 + Vite，提供了文件系统路由、自动导入、多种渲染模式（SSR、SSG、混合）和开箱即用的性能优化。开发者只需按照约定创建页面组件，框架自动处理服务端渲染和客户端注水的全流程。**设计目的**：让 SSR 的实现从"需要深度理解底层原理"降低到"配置 + 约定开发"的水平，大幅降低同构应用开发的门槛。

### 性能优化 (Performance Optimization)

**(1) 代码层面优化**

- 合理使用 `v-if` / `v-show`：频繁切换用 `v-show`，条件稳定用 `v-if`
> **设计思路**：选择 `v-if` 还是 `v-show` 本质上是执行时间与创建/销毁开销之间的权衡。`v-if` 是真正的条件渲染，适用于不需要频繁切换的稳态 UI（因为在切换时的创建/销毁开销较大）；`v-show` 始终保持在 DOM 树中，切换仅调整 CSS 样式，切换成本极低但初始渲染和内存占用略高。**设计目的**：根据不同场景选择最小化总开销的策略——频繁切换场景下避免反复创建销毁的累积开销，稳定展示场景下避免不必要元素的内存占用。

- 使用 `computed` 代替 `methods` 处理派生数据（利用缓存）
> **设计思路**：如果一个数据是通过计算其他数据得到的，且计算过程有一定开销（如过滤、排序、聚合），使用 computed 可以确保只在必要时候重新计算，避免每次渲染都重复执行。

- 使用 `v-for` 时添加唯一 `key`，提升列表渲染效率
> **设计思路**：虚拟 DOM 的 diff 算法在进行列表对比时，如果没有 key，默认采用"就地复用"策略，可能导致不正确的状态保留（如输入框内容在列表项排序后对应到错误的位置）。**设计实现**：添加唯一的 `key` 属性后，diff 算法可以通过 key 准确定位每个列表项的身份，精确进行"移动"而非"销毁+重建"，从而在保证正确性的同时最大化复用现有 DOM 节点。**设计目的**：确保列表渲染的正确性和性能——正确匹配数据项与 DOM 节点，避免不必要的 DOM 操作。

- 组件懒加载/异步组件 (Async Components)：按需加载，减少首屏包体积
> **设计思路**：大型 SPA 应用中，很多页面和组件在首屏并不需要。如果全部打包进一个 bundle，会导致首屏 JS 体积过大、解析执行时间过长。**设计实现**：使用 `defineAsyncComponent` 或动态 `import()` 语法配合构建工具的代码分割 (code splitting)，将特定组件拆分为独立的 chunk，只在需要渲染时才异步加载该 chunk。**设计目的**：降低首屏加载的 JS 体积，实现"按需加载"——首屏只加载必需代码，非首屏内容延迟加载，提升首屏渲染速度 (FCP / LCP)。

- 避免不必要的响应式数据：非响应式数据不要用 `ref/reactive` 包裹
> **设计思路**：响应式系统虽然方便，但每个响应式变量都有额外的内存和性能开销（Proxy 代理、依赖收集）。将不需要驱动视图更新的数据声明为响应式是浪费。**设计实现**：对于不会变化的常量（如配置对象）、不需要在模板中使用的数据（如仅为计算中间值），直接使用普通 JavaScript 变量声明，不经过 `ref` 或 `reactive` 包装。**设计目的**：减少不必要的 Proxy 创建和依赖追踪开销，保持响应式系统的高效性。

- 合理拆分组件，避免单个组件过于庞大
> **设计思路**：庞大的单组件存在两个性能问题：一是该组件中任何数据的任何微小变化都会触发整个组件重新渲染；二是组件的模板编译产物过大，首次渲染等待时间长。**设计实现**：将大型组件按功能区域拆分为子组件，每个子组件独立管理自身的响应式依赖范围。当某个区域的数据变化时，只有对应的子组件重新渲染，而非整个大组件。**设计目的**：缩小每次数据变更的影响范围，实现更精细的渲染更新，同时在架构上也提升了代码的可维护性。

**(2) 资源优化**

- 图片懒加载、压缩、使用 WebP 格式
> **设计思路**：图片通常是网页中体积最大的资源类别。图片懒加载确保只有进入视口的图片才会被下载，避免了首屏加载大量看不到的图片。图片压缩和 WebP 格式则在不明显降低视觉质量的前提下大幅减少文件体积。**设计实现**：使用 `<img loading="lazy">` 或 `Intersection Observer API` 实现懒加载；构建时通过 Vite 插件自动压缩和转换图片格式。**设计目的**：减少页面总下载量和带宽消耗，提升首屏内容的展示速度，节省用户流量。

- CSS/JS 代码压缩与合并
> **设计思路**：未压缩的代码包含大量空格、换行、注释和完整变量名，体积远大于实际需要的容量。压缩和合并减少了 HTTP 请求数量和单个文件的传输量。**设计实现**：构建工具（Vite / webpack）在 production 模式下自动使用 Terser（JS 压缩）、CSSNano（CSS 压缩）等工具处理代码，变量名被替换为短名、空格/注释被移除。**设计目的**：在构建阶段自动完成代码体积优化，零开发成本地减少传输大小。

- 使用 CDN 加载静态资源
> **设计思路**：用户在地理上分布广泛，如果所有请求都回源到单一服务器，距离远的用户将承受高延迟。CDN 通过在世界各地部署边缘节点，将静态资源缓存到离用户最近的节点。**设计实现**：将 Vue、Element Plus 等第三方库的 bundle 或静态图片上传到 CDN，应用中使用 CDN URL 引用。CDN 的 DNS 智能解析将用户路由到最近的边缘节点。**设计目的**：降低资源加载延迟，减轻源服务器压力，提升全球用户的访问体验。

- Tree-shaking：移除未使用的代码
> **设计思路**：第三方库通常导出了丰富的功能，但项目往往只用到其中一小部分。如果不做处理，未使用的代码也会被打包进最终产物。**设计实现**：Tree-shaking 依赖于 ES Module 的静态导入/导出语法——构建工具（如 Rollup、webpack）在打包时分析模块依赖图，识别哪些导出的变量和函数被真正使用，未被引用的部分在最终产物中被移除。Vue 3 + Vite 天然支持 Tree-shaking。**设计目的**：避免将未使用的库代码发送给用户，减小打包体积，提升加载速度。

**(3) 网络层面优化**

- 减少 HTTP 请求数
> **设计思路**：每个 HTTP 请求都有固定的开销（DNS 解析、TCP 连接建立、TLS 握手），在 HTTP/1.1 时代这一开销尤为显著。**设计实现**：通过资源合并（将多个 CSS/JS 文件打包为一个）、雪碧图（将小图标合并为一张大图）、内联小资源（Base64 编码）等方式减少请求数量。**设计目的**：降低网络请求的固定开销，减少页面加载完成的等待时间。

- 使用浏览器缓存 (HTTP 缓存策略)
> **设计思路**：对于不经常变化的静态资源（如带哈希的 JS/CSS bundle、图片），不应该在用户每次访问时重新下载。**设计实现**：构建工具在文件名中加入内容哈希（如 `app.abc123.js`），服务器对这些文件设置长过期时间的 `Cache-Control` 头。文件内容不变则哈希不变，浏览器直接使用缓存；内容改变则哈希改变，浏览器识别为新文件重新下载。**设计目的**：最大化缓存命中率，让回访用户几乎无需重新下载静态资源，实现近乎即时的页面加载体验。

- 启用 Gzip/Brotli 压缩
> **设计思路**：文本资源（HTML、CSS、JS、JSON）的压缩比通常可达 60-80%，在传输前压缩可以大幅减少网络传输量。**设计实现**：服务器（Nginx/CDN）在响应请求时对文本类资源使用 Gzip 或 Brotli 算法实时压缩，浏览器收到压缩数据后自动解压。Brotli 压缩比通常优于 Gzip，尤其在静态资源预压缩时效果更好。**设计目的**：在不改变代码本身的前提下，通过传输层压缩大幅减少网络传输数据量。

- 使用 HTTP/2 多路复用
> **设计思路**：HTTP/1.1 中每个 TCP 连接一次只能处理一个请求（队头阻塞问题），浏览器通过并发多个连接（通常 6 个）来提升并发度，但这增加了连接建立开销。HTTP/2 的多路复用允许多个请求/响应在一个 TCP 连接上并行传输，消除了队头阻塞。**设计目的**：降低连接建立开销，提升并发资源下载效率，使得资源合并策略（减少请求数）在 HTTP/2 下不再那么关键。

## 本章小结 (Chapter Summary)

Vue 核心知识框架：

1. **Vue 简介**：渐进式框架，由 Evan You 创建，核心特性包括响应式、组件化、模板语法、双向绑定
   > Vue 的渐进式设计使其成为"按需采用的框架"——从简单的页面增强到完整的 SPA，都能找到适合的使用方式。这是它与 Angular（全有或全无）和 React（需要较多配套设施）在市场定位上的核心差异。

2. **模板语法**：8 大指令 (v-text, v-html, v-bind, v-on, v-model, v-if, v-for, v-show)
   > Vue 的指令系统通过扩展 HTML 语义，让开发者在模板中声明式地表达动态行为，编译阶段再转化为高效的渲染函数。这是 Vue 易用性和高性能兼得的关键架构设计。

3. **组件与数据传递**：单文件组件 (.vue)，Props 父传子，Emit 子传父
   > 单文件组件实现了功能维度的关注点分离，Props 和 Emit 建立了明确的数据流方向——数据向下 (Props)、事件向上 (Emit)，这是构建可维护组件树的基础约束。

4. **响应式系统**：Proxy 拦截 + 依赖收集 + 派发更新；ref/reactive 声明响应式数据；computed 缓存计算
   > 响应式系统是 Vue 的核心引擎，将"数据 -> 视图"的映射关系自动化。Vue 3 的 Proxy 方案相比 Vue 2 的 defineProperty 方案，实现了更完整的变更追踪和更好的数组处理能力。

5. **生命周期钩子**：三对钩子函数，onMounted 和 onUnmounted 最为常用
   > 生命周期钩子为组件的生命周期各阶段提供了干预点，确保初始化逻辑和清理逻辑能在正确的时机执行，是防止内存泄漏和状态异常的关键机制。

6. **前端其他知识**：TypeScript (JS 超集 + 静态类型) / SSR (服务端渲染) / 性能优化 (代码 + 资源 + 网络)
   > 这部分知识构建了 Vue 技术栈之上的完整前端工程化体系——类型安全 (TS)、渲染架构 (SSR/SSG) 和部署优化 (性能)，是专业前端开发者不可或缺的技能。

## 客观考点总结

### 选择题/填空题考点

1. Vue 的创建者：**尤雨溪 (Evan You)**，创建年份：**2014 年**
2. Vue 的定位：**渐进式 JavaScript 框架** (Progressive JavaScript Framework)
3. Vue 的核心特性（多选常考）：渐进式、响应式、组件化、模板语法、双向绑定
4. Vue 模板中的 **8 大指令**命名和作用：`v-text`、`v-html`、`v-bind`、`v-on`、`v-model`、`v-if`、`v-for`、`v-show`
5. `v-bind` 的简写：**`:`**（冒号）；`v-on` 的简写：**`@`**（at 符号）
6. `v-if` 和 `v-show` 的关键区别：
   - `v-if`：条件为假时**销毁/移除 DOM 元素**，切换开销大
   - `v-show`：始终保留在 DOM 中，仅切换 **CSS `display` 属性**，初始渲染开销大
7. `.vue` 单文件组件的三个成员：**`<template>`**、**`<script>`**、**`<style>`**
8. 父传子数据的方式：**Props**；子传父数据的方式：**Emit 事件**
9. Vue 3 响应式系统的底层实现：**Proxy**（不是 `Object.defineProperty`）
10. 响应式系统的两个核心流程：**依赖收集** (Dependency Tracking) 和 **派发更新** (Dispatch Update)
11. 声明基本类型响应式数据用 **`ref()`**（访问需 `.value`）；声明对象类型用 **`reactive()`**
12. 计算属性 `computed` 的核心特点：**缓存**——依赖不变时不会重新计算
13. 生命周期钩子中，最常用的两个是：**`onMounted`**（初始化/发请求）和 **`onUnmounted`**（清理资源）
14. 生命周期钩子分为三对：**before/mounted**、**before/update**、**before/unmount**
15. TypeScript 是 JavaScript 的**超集** (Superset)，核心优势是**静态类型检查**
16. CSR 的两个主要缺陷：**首屏加载慢**、**SEO 不友好**
17. Vue 的 SSR 框架是 **Nuxt.js**；React 的 SSR 框架是 **Next.js**
18. 列表渲染 `v-for` 必须绑定 **`key`** 属性，且 key 必须**唯一**
19. 性能优化三维度：**代码层面**、**资源优化**、**网络层面**

### 简答题考点

1. **简述 Vue 的渐进式框架设计理念及其意义。**
   答题要点：从简单到复杂逐步引入；核心库 + 官方配套库的分层设计；可在不改变现有项目架构的前提下增量采用；适应各种规模项目。

2. **对比 v-if 和 v-show 的原理及适用场景。**
   答题要点：v-if 是真正的条件渲染（销毁/重建 DOM），切换开销大，适合条件很少改变的稳态 UI；v-show 始终渲染仅切换 display，初始渲染开销大但切换快，适合频繁切换场景。

3. **描述 Vue 3 响应式系统的工作原理。**
   答题要点：基于 Proxy 拦截数据的 get/set 操作；渲染时通过 get 拦截进行依赖收集（建立 data -> component 映射）；数据变更时通过 set 拦截派发更新（通知组件重新渲染）；异步批处理避免重复渲染。

4. **对比 computed 和 methods 的区别，并说明各自的使用场景。**
   答题要点：computed 有缓存（依赖不变不重新计算），methods 每次调用都执行；computed 必须返回值且不应有副作用，用于派生值计算；methods 可以无返回值且可以有副作用，用于事件处理和操作。

5. **简述 Props 和 Emit 在 Vue 组件通信中的角色。**
   答题要点：Props 父传子，单向向下，只读不可修改；Emit 子传父，观察者模式，子组件触发自定义事件而父组件监听响应；两者共同维护单向数据流。

6. **为什么 Vue 3 使用 Proxy 替代 Vue 2 的 Object.defineProperty？**
   答题要点：Proxy 可拦截所有操作（包括属性添加/删除），defineProperty 只能拦截已有属性；Proxy 天然支持数组索引赋值和 length 修改；Proxy 无需递归初始化所有嵌套属性；API 更简洁，不需要 Vue.set/Vue.delete。

7. **简述 CSR 和 SSR 的区别，以及 SSR 解决了什么问题。**
   答题要点：CSR 在浏览器端渲染（白屏时间长，SEO 差）；SSR 在服务器端完成首屏渲染（直接返回完整 HTML，浏览器注水）；SSR 解决首屏加载慢和搜索引擎抓取问题。

8. **列举至少 5 条 Vue 项目的性能优化策略。**
   答题要点：合理使用 v-if/v-show；computed 代替 methods 处理派生数据；v-for 添加唯一 key；组件懒加载/异步组件；避免不必要的响应式数据；合理拆分组件；图片懒加载和压缩；CDN 和缓存策略。

### 易混淆概念

| 易混淆对 | 关键区别 |
|----------|----------|
| **v-if vs v-show** | v-if 销毁/重建 DOM；v-show 仅切换 `display` CSS 属性 |
| **computed vs methods** | computed 有缓存（依赖不变不重新计算）；methods 每次调用都执行 |
| **ref() vs reactive()** | ref 用于基本类型（访问需 `.value`）；reactive 用于对象类型（直接访问属性） |
| **Props vs Emit** | Props 父传子（向下，只读）；Emit 子传父（向上，通过事件） |
| **Proxy (Vue 3) vs Object.defineProperty (Vue 2)** | Proxy 拦截所有操作、支持数组、无需 Vue.set；defineProperty 仅拦截已有属性 |
| **TypeScript vs JavaScript** | TypeScript 是 JS 的超集，添加了静态类型系统，编译时检查 |
| **CSR vs SSR** | CSR 客户端渲染（白屏、SEO 差）；SSR 服务端渲染（首屏快、SEO 好） |
| **SSR vs SSG** | SSR 每次请求动态渲染（适合动态内容）；SSG 构建时预渲染为静态文件（适合内容不变的页面） |
| **MVC vs MVVM** | MVC 中 Controller 中介 Model 和 View；MVVM 中 ViewModel 通过数据绑定自动同步 View 和 Model，Vue 属于 MVVM 模式 |
| **Options API vs Composition API** | Options API 按选项组织（data/methods/computed 分开）；Composition API 按逻辑关注点组织（setup 中相关代码在一起），更利于逻辑复用 |
