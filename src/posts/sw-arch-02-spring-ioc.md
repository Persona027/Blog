## 程序架构的发展

### 从 HelloWorld 到 IoC

- **阶段1 — 硬编码**（经典 HelloWorld 程序）
  - 输出内容直接写在代码中，修改需要重新编译和测试
  - **设计思路**：问题是极端刚性——数据和逻辑绑定在一起，任何内容变更都触发完整的开发-编译-测试-部署流程，这在业务需求频繁变化的场景下完全是不可接受的。
  - **设计目的**：硬编码本身不体现架构目的，而是作为反面教材展示"无架构"状态下的脆弱性，为后续每一次解耦演进提供对比基线。
- **阶段2 — 命令行参数**（HelloWorldCmdLine）
  - 程序从外部接受字符串参数，运行时决定输出内容，初步解耦
  - **设计思路**：将可变数据从代码中抽出，通过运行时参数传入，是一种"外部化"思想的雏形——代码负责逻辑，参数负责变化。
  - **设计目的**：实现数据与逻辑的初步分离，证明即使是简单的参数传递也是一种解耦手段，为后续更复杂的依赖外部化做铺垫。
- **阶段3 — 面向对象与分层架构**（OOP）
  - 三个功能模块：持久化数据读取 (FileHelloStr)、业务逻辑处理 (HelloWorld)、界面输出 (HelloWorldClient)
  - **设计思路**：将单一程序按职责拆分为三层——数据访问层、业务逻辑层、表示层，每一层只关注自己的核心职责，这是"关注点分离"原则的直接体现。
  - **设计目的**：通过分层提高代码的可理解性和可维护性，使每一层可以独立开发和测试；但这一阶段的分层并未解决组件间的依赖管理问题。
  - **问题**：高耦合——HelloWorld 依赖 FileHelloStr，HelloWorldClient 依赖 HelloWorld，可维护性和扩展性差，不适合大型企业级应用
  - **设计思路**：分层架构虽然划分了职责边界，但组件间直接通过 `new` 实例化依赖，导致上层必须知道下层的具体实现类——这违反了"依赖倒置原则"，即高层模块不应依赖低层模块的具体实现。
  - **设计目的**：暴露分层架构的根本缺陷——仅靠分层无法实现真正的解耦，必须引入额外的管理机制来处理组件之间的依赖关系，由此引出工厂模式和 IoC 容器。
- **阶段4 — 简单工厂模式**（初步解耦）
  - 将依赖对象的创建集中到工厂中，OrderService 不再直接依赖具体实现类，只依赖接口和工厂
  - **设计思路**：将对象创建的职责从业务类中集中转移到工厂类，业务类只需知道"谁可以帮我创建依赖"而不是"如何创建依赖"，这是创建与使用分离思想的首次实践。
  - **设计目的**：实现业务代码与具体实现类的解耦，使新增或替换实现类时业务代码无需修改；但工厂本身仍然是一个硬编码的依赖点，解耦并不彻底。
  - **局限**：新增支付方式时仍需修改工厂代码；工厂成为新的依赖点；静态方法难以替换为 Mock 对象进行测试
  - **设计思路**：工厂模式只解决了"创建集中化"问题，没有解决"创建灵活化"问题——工厂代码本身是静态的、编译期确定的，无法在运行时动态决定创建哪种实现，且工厂的静态特性使单元测试中的 mock 替换变得非常困难。
  - **设计目的**：揭示工厂模式的边界——它是从硬编码依赖到动态容器管理的关键过渡形态，其局限性直接催生了 IoC 容器的设计需求。
- **阶段5 — IoC 思想的萌芽**（更高级的解耦）
  - 将"创建和管理对象"的职责完全从业务代码中抽离，交给通用基础设施（容器），通过依赖注入 (DI) 实现控制反转
  - **设计思路**：核心洞察是"创建对象"这件事本身不是业务逻辑，而是一种横切关注点——既然是基础设施职责，就应该由通用容器统一处理，业务代码只需要声明"我需要什么"即可。
  - **设计实现**：通过外部配置文件或注解声明依赖关系，容器在运行时解析这些声明，自动完成对象的创建、组装和注入。
  - **设计目的**：实现业务代码与基础设施的彻底分离，达到"你只管写业务逻辑，别管对象怎么来的"这一理想的开发体验；同时使系统具备高度的可测试性和可扩展性。

## IoC 的基本概念与核心原理

### 什么是 IoC (Inversion of Control, 控制反转)

- 面向对象编程中的一种设计原则，用于降低计算机代码之间的耦合度
- **设计思路**：传统编程中，程序通过主动调用库函数来控制流程；IoC 则将这种控制关系反转——由框架控制流程，程序被动响应，使得框架成为可复用的"主程序骨架"。
- **设计目的**：通过反转控制权来降低组件间的耦合度，使各个组件可以独立开发、独立测试、独立部署和独立替换。
- 最常用的实现方式是依赖注入 (Dependency Injection, DI)
- **设计实现**：DI 是 IoC 思想的一种具体实现模式——容器持有所有依赖的创建权，然后在适当的时机将依赖"推送"给需要的组件，而不是让组件自己"拉取"依赖。
- **设计目的**：DI 使得依赖关系在外部声明，组件本身完全不知道其依赖是从哪里来的、如何创建的，从而实现"不用你找，我送上门"的控制反转。
- 对象在被创建时，由系统外部实体将其所依赖的对象的引用传递（注入）进来，而不是系统内部自行创建
- **设计思路**：这是对对象生命周期的重新分工——"谁来创建依赖"这一问题的答案从"自己"变为"容器"，使得业务对象的生命周期管理成为一个独立的关注点。
- **设计目的**：消除组件内部的 `new` 操作，让组件的创建逻辑与使用逻辑完全分离，从而实现组件的即插即用。
- 目前最常见的具体实现是 Spring Framework
- **设计思路**：Spring 将 IoC 容器作为其核心地基，所有其他功能（AOP、事务管理、数据访问、MVC）都建立在 IoC 容器之上，形成一个统一的、可扩展的企业级开发生态。

### IoC 的核心思想与实现基础

- **核心思想**：解耦合——将组件的构建（生产）和组件的使用分开；每个组件只考虑内部的事情，明确和定义组件间的接口，实现高内聚、低耦合
- **设计思路**：借鉴制造业的组装线思想——零部件生产商只负责按规格生产零件（高内聚），装配商按接口标准将零件组装成产品，双方互不知道对方的具体实现细节。
- **设计目的**：达到"高内聚、低耦合"的软件架构目标：组件内部逻辑紧密相关（高内聚），组件之间通过接口契约交互（低耦合），使系统在复杂度增长时仍保持可管理性。
- **实现基础**：面向接口编程 + 工厂模式 + 依赖注入
- **设计思路**：这三者构成一个完整的解耦链路——面向接口编程定义契约（组件间只知接口不知实现），工厂模式集中管理创建（创建与使用分离），依赖注入自动化装配（运行时动态绑定）。
- **设计目的**：三者各司其职：接口提供抽象隔离，工厂提供创建集中化，DI 提供自动化装配；三者叠加形成一个完整的 IoC 技术栈。
- **四要素**：接口的定义 → 组件的生产 → 组件的使用 → 运行时注入
- **设计思路**：这四个要素构成了 IoC 容器的完整工作流程——先定义契约（接口），再生产组件（工厂/容器），然后业务代码声明需要（使用），最后容器完成装配（注入）。
- **设计目的**：将复杂的依赖管理问题分解为四个有序步骤，每一步都是可配置、可替换的，使整个依赖管理体系清晰可控。

### IoC 原理范例——打印机案例

- **第一步**：定义组件接口——墨盒接口 (Ink) 和纸张接口 (Paper)
- **设计思路**：接口是组件之间的"握手协议"——打印机不需要知道墨盒是彩色的还是黑白的，只需要知道"墨盒能提供墨水"即可；这层抽象是解耦的第一道防线。
- **设计目的**：通过接口隔离具体实现，使得任何满足接口契约的墨盒都能与打印机配合工作，实现组件的可替换性。
- **第二步**：使用接口开发打印机（不依赖具体实现）
- **设计思路**：打印机内部只持有 Ink 和 Paper 的接口引用，通过接口方法获取数据，完全不知道具体是什么类型的墨盒和纸张——这是"依赖倒置原则"的实践。
- **设计目的**：使打印机组件成为一个封闭的、纯粹关注打印逻辑的模块，任何符合接口的实现都可以在运行时接入，而不需要修改打印机代码。
- **第三步**：组装打印机——添加实现类
- **设计思路**：提供各种具体实现（如彩色墨盒、黑白墨盒、A4纸张、A5纸张），这些实现各自管理自己的内部逻辑，符合接口规范即可。
- **设计目的**：展示接口编程的优势——新增墨盒或纸张类型只需添加新的实现类，打印机代码零改动，验证了开闭原则（对扩展开放，对修改关闭）。
- **第四步**：使用 Spring IoC 容器装配对象
- **设计思路**：通过 XML 或注解配置告诉容器"打印机需要哪个墨盒、哪种纸张"，容器负责找到对应的 Bean 并注入——开发者的职责从"组装"变成"声明"。
- **设计目的**：体现 IoC 容器的终极价值——将"组件如何装配在一起"这一跨领域问题完全外包给容器，让开发者专注于业务逻辑的实现。

## Spring IoC 容器

### 容器概述

- **Bean**：由 Spring IoC 容器负责实例化、组装和管理的对象称为 Bean。Bean 就是普通的 Java 对象 (POJO)，但被纳入了容器的管理范围
- **设计思路**：Spring 刻意强调 Bean 就是普通 POJO，不需要继承特定基类或实现特定接口——这意味着业务对象不会被框架"污染"，保持纯 POJO 特性使其可以在容器外独立测试和使用。
- **设计目的**：降低框架侵入性，让业务代码与 Spring 框架的耦合最小化；开发者可以编写纯粹的领域逻辑，而不需要为了获得 DI 能力而牺牲代码的简洁性和可移植性。

### 核心接口

- **BeanFactory**（顶层接口）
  - 提供最基础的 IoC 功能
  - **设计思路**：BeanFactory 实现了"最小可用容器"的理念——它只做一件事：按需管理和提供 Bean，不引入任何额外的企业级功能，保持接口的纯粹和轻量。
  - **设计目的**：为资源受限场景提供选择，同时也定义了 IoC 容器的最低功能边界，所有高级容器实现都建立在 BeanFactory 之上。
  - 采用延迟加载策略（Lazy Loading），仅在调用 `getBean()` 时才实例化 Bean
  - **设计实现**：容器启动时只解析配置元数据，不真正创建 Bean 实例；当有请求时先查找缓存，未命中则创建并缓存，之后返回。
  - **设计目的**：减少启动时间和内存占用——对于资源受限环境（如嵌入式系统），不需要的 Bean 永远不会被创建，节省系统资源。
  - 适用于资源受限的环境（如移动设备）
  - **设计思路**：在内存和计算资源有限的环境中，预加载所有 Bean 可能导致启动缓慢和内存溢出，延迟加载可以按需分配资源。
- **ApplicationContext**（BeanFactory 的子接口）
  - 企业级应用的首选
  - **设计思路**：ApplicationContext 在 BeanFactory 基础上扩展了企业级功能，形成一个完整的应用框架层——它不仅是 Bean 容器，更是企业级应用的基础设施平台。
  - **设计目的**：为日常企业级开发提供一站式解决方案，开发者无需手动集成多种服务，只需使用 ApplicationContext 即可获得 DI + 国际化 + 事件 + AOP 等全套能力。
  - 容器启动时预加载所有单例 Bean（立即加载 / Eager Loading）
  - **设计实现**：容器初始化阶段即遍历所有 Bean 定义，提前创建并装配所有非懒加载的单例 Bean，将依赖解析失败等问题暴露在启动阶段而不是运行阶段。
  - **设计目的**：实现"快速失败"原则——让配置错误在启动时就暴露出来，避免应用运行到某个功能点时才发现 Bean 配置有问题，提升系统可靠性。
  - 提供额外的企业级功能：国际化 (MessageSource)、事件发布 (ApplicationEvent)、AOP 集成、环境抽象 (Environment) 等
  - **设计思路**：这些功能并非 IoC 所必需，但在企业级应用中非常常见；将它们集成到 ApplicationContext 中，使开发者无需额外集成即可使用这些能力。
  - **设计目的**：统一的编程模型和一致的配置体验——所有企业级能力共享同一个容器生命周期和配置体系，降低了学习成本和使用复杂度。

### 常见的 ApplicationContext 实现

- `ClassPathXmlApplicationContext`：从类路径加载 XML 配置文件
- **设计实现**：从编译后的类路径（src/main/resources）读取 XML，适合配置文件打包在 JAR/WAR 中的标准部署场景。
- `FileSystemXmlApplicationContext`：从文件系统加载 XML 配置文件
- **设计实现**：从操作系统文件路径读取 XML，适合配置文件存放在应用外部（如 /etc/myapp/）的运维友好场景，便于在不重新打包的情况下修改配置。
- `AnnotationConfigApplicationContext`：基于 Java 配置类和注解
- **设计思路**：顺应"配置即代码"趋势——用 Java 类替代 XML 文件描述 Bean 关系，利用编译期类型检查消除 XML 中字符串拼写错误的隐患。
- **设计目的**：提供类型安全的配置方式，支持 IDE 重构和自动补全，并与 Spring Boot 的自动配置理念对接。

### 容器使用范例

- 第1步：导入 Spring IoC 相关的依赖包
- **设计实现**：在 Maven/Gradle 中引入 `spring-context` 等核心依赖，这些依赖会自动传递引入 `spring-beans`、`spring-core` 等模块。
- 第2步：创建 `applicationContext.xml` 配置文件
- **设计实现**：在 XML 中定义 beans 命名空间，声明需要容器管理的 Bean 及其依赖关系，这是传统 Spring 应用的核心配置入口。
- 第3步：添加 Bean 的 XML 配置
- **设计实现**：为每个需要容器管理的 Java 类在 XML 中添加一个 `<bean>` 元素，指定 id（唯一标识）和 class（全限定类名），以及可选的 `<property>` 或 `<constructor-arg>` 定义注入关系。
- 第4步：初始化容器，使用容器装配对象
- **设计实现**：通过 `new ClassPathXmlApplicationContext("applicationContext.xml")` 启动容器，然后调用 `context.getBean(beanId)` 获取已装配好的对象实例。

## Bean 的定义和配置方式

### XML 配置 (Spring 1.x)

- **优点**：完全解耦，所有 Bean 关系在 XML 中定义，修改无需重新编译代码
- **设计思路**：将 Bean 的装配关系从 Java 代码中完全抽离到外部 XML 文件，使"依赖管理"成为一个独立于代码的配置层——切换数据库实现或替换服务实现时，只需修改 XML 文件即可。
- **设计目的**：实现编译期二进制与运行期装配逻辑的完全分离，使得运维人员可以在不触及源代码和编译构建的情况下调整应用的组件组合，极大提升了部署灵活性。
- **缺点**：配置冗长，维护成本高，难以管理大量 Bean
- **设计思路**：当 Bean 数量膨胀到数百甚至数千时，XML 文件变得极其臃肿，查找和修改特定 Bean 的配置像大海捞针，且 XML 本身不提供编译期校验，错误只能等到容器启动时才暴露。
- **设计目的**：XML 配置虽然解耦彻底，但在项目中后期会拖累开发效率，这直接催生了后续的注解配置和 Java Config 方式——两者在"零配置"和"完全解耦"之间寻找平衡。

### 注解配置 (Spring 2.5+)

- 类级别：`@Component`、`@Service`、`@Repository`、`@Controller`
- **设计思路**：用"标记"替代"声明"——在 Java 类上直接加注解，告诉 Spring"请把这个类管理起来"，是一种声明式的注册方式，比 XML 中写 `<bean class="..."/>` 更直观。
- **设计目的**：减少配置量，让 Bean 的定义回到代码中，实现"所见即所得"——看一个类就知道它是否被 Spring 管理、充当哪种角色（Service/Repository/Controller）。
- 字段/方法级别：`@Autowired`、`@Resource`
- **设计思路**：将依赖注入的信息从 XML 移到代码中，通过注解在字段或 setter 上标记需要注入的依赖，Spring 自动按类型或名称匹配并注入。
- **设计目的**：简化注入配置，让依赖关系在代码中一目了然，减少外部配置文件的维护负担。
- **优点**：开发效率高，配置与代码结合紧密、直观
- **设计思路**：注解配置将"定义 Bean"和"定义依赖"的信息内聚在 Java 类本身中，开发者不需要在 Java 文件和 XML 文件之间频繁切换。
- **设计目的**：提升开发体验和效率，尤其适合中小型项目和敏捷开发场景。
- **缺点**：Bean 的依赖关系分散在代码中，修改可能需要重新编译
- **设计思路**：注解是硬编码在 Java 源代码中的元数据，修改依赖关系（如切换实现类）需要修改源码并重新编译，失去了 XML 配置"无需重编译即可切换实现"的灵活性。
- **设计目的**：暴露注解配置的权衡——用编译期安全性换取了运行期灵活性，项目选型时需要在两者之间做出判断。

### Java Config (Spring 3.0+)

- 使用 `@Configuration` 标记配置类，`@Bean` 标记方法返回 Bean 实例
- **设计实现**：`@Configuration` 类的方法会被 CGLIB 代理增强，确保多次调用同一个 `@Bean` 方法时返回同一个单例实例，而不是每次都创建新对象。
- **设计目的**：用 Java 代码表达 Bean 的创建和装配逻辑，享受编译期类型检查、IDE 重构支持和断点调试等开发者工具链的优势。
- **优点**：类型安全，支持重构，可灵活编程（如条件判断创建 Bean）
- **设计思路**：既然 Bean 的创建本身就是 Java 代码的逻辑，用 Java 描述比用 XML 更自然——可以在 `@Bean` 方法中写 if/else 判断、for 循环等，根据运行时条件动态决定创建哪些 Bean 和如何配置它们。
- **设计目的**：提供最大灵活性的同时保持类型安全，适合需要条件化配置（如多环境切换）的复杂项目。
- Spring Boot 基于 Java Config 进一步简化了配置
- **设计思路**：Spring Boot 利用 `@Conditional`、`@EnableAutoConfiguration` 等机制，在 Java Config 的基础上实现了"自动配置"——根据 classpath 中存在的依赖自动推断和创建所需的 Bean，将"约定优于配置"理念发挥到极致。

## 依赖注入 (Dependency Injection, DI)

Spring IoC 支持三种依赖注入方式：

### 构造器注入 (Constructor Injection)

- **优点**：
  - **强制性**：对象必须提供依赖才能被创建，避免空指针异常
  - **设计思路**：将依赖设置为构造函数的参数，等于在编译期声明"没有这些依赖，这个对象就不完整"——这是一种在类型系统层面表达的契约，编译器会强制执行。
  - **设计目的**：消除"半初始化对象"的可能性，确保对象在构造完成后立即处于就绪状态，大幅减少空指针异常的风险。
  - **不可变性**：依赖一旦注入，在对象生命周期内不会改变，适合线程安全场景
  - **设计思路**：将依赖字段声明为 `final`，在构造器中进行唯一一次赋值，之后依赖引用不可变——这种不可变性是函数式编程思想在面向对象中的体现。
  - **设计目的**：保证线程安全，消除因运行时替换依赖导致的副作用和并发问题，使对象的行为在其生命周期内稳定可预测。
  - **易于测试**：在单元测试中可直接 new 对象并手动传入 mock 依赖，无需启动 Spring 容器
  - **设计思路**：因为依赖通过构造器传入，测试代码可以完全绕开 Spring 容器，直接创建被测对象并传入 mock/stub 实现，使单元测试轻量且快速。
  - **设计目的**：提升可测试性——不需要 Spring Test Context 的测试启动快、隔离性好，符合"单元测试应该只测一个类"的原则。
  - 明确依赖关系
  - **设计思路**：一个类的所有必需依赖都暴露在它的构造器签名中，看构造器参数列表就能一目了然地知道这个类需要什么。
  - **设计目的**：提升代码可读性和可维护性——依赖即文档，新加入的开发者一看构造器就知道这个类要干什么、需要什么底层支持。
- **缺点**：当依赖过多时，构造器参数列表会变得很长（这是代码需要重构的"坏味道"，提示该类可能承担了过多职责）
- **设计思路**：构造器参数过多本身不是构造器注入的问题，而是设计问题——它暴露了这个类可能违反了"单一职责原则"，承担了太多职责，应该考虑拆分为多个更小、更专注的类。
- **设计目的**：构造器注入充当了设计质量的"预警器"——当参数列表过长时，它促使开发者重新审视类的职责划分，起到设计反馈循环的作用。

### Setter 注入

- **优点**：
  - **灵活性**：依赖可以在对象创建后重新设置（如通过配置变更动态切换实现），适合可选依赖
  - **设计思路**：Setter 注入将依赖视为对象的"属性"而非"构造要件"，允许在对象生命周期的任何阶段修改依赖——类比硬件的热插拔能力，不关机就能更换外设。
  - **设计目的**：支持运行时动态切换依赖实现，适用于需要根据运行时条件（配置变更、特性开关等）更换策略的场景。
  - **避免循环依赖**：配合三级缓存可以解决部分循环依赖场景（构造器注入对此可能直接抛出异常）
  - **设计思路**：Spring 通过"先创建空壳对象（未注入依赖），再逐步注入"的方式处理 Setter 循环依赖；构造器注入要求创建时必须有完整依赖，所以无法绕过循环。
  - **设计目的**：在无法通过重构消除循环依赖的"历史遗留"场景中，Setter 注入提供了一种务实的兜底方案；但理想情况下应该重构代码消除循环依赖。
- **缺点**：
  - 不确定性：对象创建后依赖可能为 null（忘记调用 setter），无法保证对象完全初始化
  - **设计思路**：Setter 注入缺少"契约强制"——不像构造器那样在编译期和运行期约束依赖必须提供，依赖是否注入完全依赖于框架或开发者的"自觉"，存在遗漏风险。
  - **设计目的**：提醒开发者 Setter 注入本质上牺牲了"安全性"换取了"灵活性"，在选择时应权衡：如果某个依赖是必须的，应优先使用构造器注入。
  - 不适合强制依赖：如果某个依赖是必须的，无法强制要求
  - **设计思路**：无法通过编译期或类型系统表达"这个 setter 必须被调用"的约束，只能在运行时通过检查是否为 null 来防御，增加了样板代码和维护心智负担。

### 字段注入 (Field Injection)

- **优点**：代码极其简洁，开发效率高
- **设计思路**：直接在有依赖的字段上加 `@Autowired`，省去了写构造器和 setter 的代码，是最少键盘敲击的注入方式，在快速原型开发和内部工具中非常受欢迎。
- **设计目的**：降低代码量，提升初期开发速度——但这是以牺牲可测试性和可维护性为代价的短期效率。
- **缺点**：
  - 无法声明 final：依赖可变，破坏不可变性
  - **设计思路**：`@Autowired` 作用于字段，Spring 通过反射注入值，字段无法声明为 `final`——这意味着依赖可能在对象的任何生命周期时刻被替换，无法保证线程安全。
  - **设计目的**：暴露出字段注入在设计哲学上与"不可变优先"原则的冲突——如果你认为依赖不应该在运行时改变，就不应该使用字段注入。
  - **隐藏依赖**：通过类的外部接口（构造器、setter）看不到依赖，容易导致运行时意外（依赖未注入）
  - **设计思路**：一个类对外暴露的公开接口（构造器、公共方法）完全没有体现它的依赖——你只能深入阅读源码才能知道它依赖了什么，这对代码阅读者和维护者是巨大的认知负担。
  - **设计目的**：警示字段注入对代码可读性的破坏——依赖应该是一种"显式的契约"而不是"隐藏的魔法"。
  - **与容器强耦合**：脱离 Spring 容器（如单元测试）时无法简单地通过 new 注入依赖，必须使用反射或启动容器
  - **设计思路**：字段注入隐式依赖于 Spring 容器的反射机制——在容器外（如单元测试）通过 `new` 创建对象时，`@Autowired` 字段保持为 null，因为没有任何机制触发注入。
  - **设计目的**：展示字段注入对可测试性的损害——如果测试一个类需要启动整个 Spring 容器，那不再是单元测试，而是集成测试，失去了单元测试的快速反馈优势。
  - 容易产生循环依赖：字段注入让依赖关系不显式，可能不经意间引入循环依赖
  - **设计思路**：因为依赖是"隐藏的"，开发者可能在不知情的情况下让 A 依赖 B、B 依赖 A，直到运行时 Spring 报错才发现循环依赖问题。
- **官方立场**：程序员实际使用中很常见，但官方文档和组织标准中均不推荐
- **设计思路**：官方不推荐但实际流行，这反映了"开发便利性"和"架构正确性"之间的典型张力——字段注入是快但脏的方案，在企业级项目中控制这种技术债非常重要。

### 处理多个同类型 Bean

当一个接口有多个实现类时，三种指定方式：

- **方法一**：使用 `@Primary` 标记首选实现
- **设计思路**："大家都实现这个接口，但这个是最常用的"——`@Primary` 是一种软性推荐，告诉 Spring"当没人明确说要哪个时，就用这个"。
- **设计目的**：配置默认实现，减少配置量，大多数情况下无需额外指定即可自动注入正确的 Bean。
- **方法二**：使用 `@Qualifier` 精确指定 Bean 名称
- **设计思路**：`@Qualifier` 提供精确控制——你明确告诉 Spring"我要名叫 xxx 的那个 Bean"，通过名称将接口引用与具体实现绑定。
- **设计目的**：在使用者的角度精确控制注入哪个实现，适合使用者对依赖有明确偏好的场景。
- **方法三**：注入全部实现（批量处理，如 `List<Interface>`）
- **设计思路**：利用 Spring 的类型匹配能力，将满足特定接口的所有 Bean 以集合形式注入，然后由使用者自行遍历选择合适的实现——这是策略模式和责任链模式的自然体现。
- **设计目的**：支持批量处理和动态选择，适合需要聚合所有实现结果的场景（如所有通知渠道一起发送消息）。

## Bean 的作用域 (Scope)

- **singleton**（默认）
  - 每个容器仅创建一个共享实例
  - **设计思路**：单例是"共享资源"模式的最简实现——容器维护一个实例映射表，每次请求 Bean 时先从表中查找，有则返回已有实例，无则创建并放入表中。
  - **设计目的**：节省内存，共享无状态对象的公共状态（如配置），是 Spring 默认作用域因为大多数企业级 Bean（Service、Repository、Controller）都是无状态的，天然适合单例。
  - 适用于无状态服务或 DAO
  - **设计思路**：无状态对象不持有会话相关的可变数据，每次请求处理的行为完全一致，多线程并发访问不存在数据竞争问题。
  - 有利于确保线程安全和资源高效利用。
  - Spring 的单例是"容器级单例"，每个容器一个实例，而非 JVM 层面的单例
  - **设计思路**：Spring 的单例范围限定在容器内——如果你创建了两个 ApplicationContext，每个都会创建自己的一套单例 Bean。这与 GoF 单例模式（整个 ClassLoader 只有一个实例）不同。
  - **设计目的**：允许在同一 JVM 中运行多个相互隔离的 Spring 容器，每个容器有独立的单例空间，有利于模块测试和多租户隔离。
- **prototype**
  - 每次请求 Bean 时都会创建新的实例
  - **设计思路**：prototype 是"每次消费一份新的"的设计——容器不缓存 prototype Bean，每次 `getBean()` 都执行完整的创建流程（实例化 → 依赖注入 → 后置处理）。
  - **设计目的**：适用于有状态对象——每次使用都需要一个"干净"的初始状态，不希望被上次使用污染。
  - 适用于有状态或可变对象，例如表示会话信息的对象
  - **设计思路**：有状态对象持有可变数据（如用户输入、计算结果缓冲区），多线程共享会导致数据错乱，每次请求新实例是自然的解决方案。
  - 容器仅负责初始化，不负责销毁；客户代码需自行清理资源
  - **设计思路**：Spring 容器对 prototype Bean 的管理止于"交付"——创建并注入后就不再跟踪其生命周期。如果 prototype Bean 持有资源（文件句柄、数据库连接），必须由使用方手动释放，否则会导致资源泄漏。
  - **设计目的**：明确容器和客户代码的责任边界——容器管生不管养，使用方要对资源生命周期负责。
- **request**（Web 环境）
  - 每个 HTTP 请求创建一个新实例，请求结束时销毁
  - **设计思路**：将 Bean 的生命周期绑定到 HTTP 请求的生命周期——请求到达时创建，请求处理完成后销毁，Bean 可以在请求处理链路的任意环节被共享和访问。
  - **设计目的**：为 Web 请求上下文提供天然的隔离容器，适合存放请求级别的临时数据（如请求日志、认证令牌），避免线程间数据串扰。
- **session**（Web 环境）
  - 每个 HTTP 会话维持一个实例，会话失效或超时后销毁
  - **设计思路**：将 Bean 的生命周期绑定到 HTTP Session——用户登录到退出之间，集群内同一 Session ID 的请求共享同一个 Bean 实例。
  - **设计目的**：适合存放用户级别的状态（如购物车、登录用户信息），避免每次请求都从数据库加载，又不需要使用全局单例。
- **application**（Web 环境）
  - 与 ServletContext 同生命周期，整个 Web 应用共享一个实例
  - **设计思路**：生命周期与 Web 应用完全同步——应用启动时创建，应用关闭时销毁，是 singleton 在 Web 容器环境中的等价物，但其作用域由 ServletContext 而非 Spring 容器界定。
  - **设计目的**：适合存放应用级别的全局状态或缓存数据，与 singleton 的区别在于它可以通过 ServletContext API 在 Spring 管理范围之外被访问。

## 本章小结

### 三个核心问题

1. **为什么需要 IoC？**
   - 了解程序架构随着业务和代码规模的变化而变化，掌握其中产生的各种程序架构
   - **设计思路**：从硬编码到 IoC 的五个阶段并非单纯的"技术升级史"，而是一条"耦合逐渐减弱"的架构演进主线——每一阶段都在解决上一阶段遗留的耦合问题，同时引入新的权衡。
   - **设计目的**：理解架构演进的驱动力——不是新框架出现了所以要用，而是旧方案无法满足复杂度增长的需求时才需要演进；IoC 是应对大规模企业级应用复杂性的必然选择。
   - 从硬编码 → 命令行参数 → 面向对象分层 → 简单工厂 → IoC 容器，每一步都是对耦合问题的深入解决
   - **设计思路**：这五个阶段映射了软件工程中"内聚性递增、耦合性递减"的经典设计趋势——每一阶段都使变化的影响范围更小，使代码更易于修改和扩展。
2. **IoC 和 Spring IoC 的核心原理**
   - 掌握控制反转 IoC 的核心原理（解耦合，将组件构建与使用分开）
   - **设计思路**：IoC 的核心不是"反转"本身，而是"职责重新分配"——将创建对象的职责从业务代码移到容器，让业务代码回归纯粹的业务逻辑。
   - **设计目的**：通过职责分离使系统各部分可以独立演化——业务逻辑的变更不影响组件创建方式，组件实现切换不影响业务逻辑。
   - 掌握 Spring IoC 的 Bean 工厂核心机制（BeanFactory / ApplicationContext）
   - **设计思路**：BeanFactory 是"最小可用"，ApplicationContext 是"开箱即用"——两者的取舍体现了"够用就好"与"一站式服务"两种架构哲学。
   - **设计目的**：理解两层抽象的设计意图——让框架既能跑在嵌入式设备上，也能支撑银行级企业应用，通过接口分层满足不同场景的性能和功能需求。
3. **Spring IoC 的相关概念及使用**
   - Bean 的定义和配置方式（XML / 注解 / Java Config）
   - **设计思路**：三种配置方式对应了 Spring 生态从"配置优先"到"约定优先"的演进——XML 代表外部化配置的极致，注解代表约定优于配置的雏形，Java Config 代表类型安全的配置终态。
   - **设计目的**：理解每种配置方式的历史定位和适用场景，在实际项目中根据团队技术栈和项目需求灵活选型。
   - 依赖注入 DI 的三种方式（构造器 / Setter / 字段注入）
   - **设计思路**：三种注入方式的根本差异在于"依赖的合约强度"——构造器注入提供编译期强制合约，Setter 注入提供运行期柔性合约，字段注入几乎没有合约。
   - **设计目的**：指导实际开发中根据依赖的重要程度选择注入方式——强制依赖用构造器，可选依赖用 Setter，字段注入应尽量避免。
   - Bean 的作用域（singleton / prototype / request / session / application）
   - **设计思路**：作用域本质上是"实例创建策略"的可配置化——不同的生活周期对应不同的实例管理策略，Spring 将"一个 Bean 对应几个实例、活多久"这件事变成了一个可声明属性。
   - **设计目的**：让开发者根据业务场景选择合适的实例策略，而不是所有 Bean 都用同一种方式管理，在灵活性和性能之间找到平衡。

## 客观考点总结

### 选择题/填空题考点

- IoC 的全称与中文翻译：Inversion of Control，控制反转
- DI 的全称与中文翻译：Dependency Injection，依赖注入
- IoC 的核心思想：解耦合——将组件的构建（生产）和使用分开
- IoC 实现三要素：面向接口编程 + 工厂模式 + 依赖注入
- IoC 四要素：接口的定义 → 组件的生产 → 组件的使用 → 运行时注入
- BeanFactory 的加载策略：延迟加载（Lazy Loading），`getBean()` 时才实例化
- ApplicationContext 的加载策略：立即加载（Eager Loading），启动时预加载所有单例 Bean
- Bean 的默认作用域：singleton（容器级单例，非 JVM 级单例）
- Spring Bean 就是普通 Java 对象 (POJO)，但纳入容器管理
- 三种 Bean 配置方式：XML 配置 (Spring 1.x)、注解配置 (Spring 2.5+)、Java Config (Spring 3.0+)
- 三种依赖注入方式：构造器注入、Setter 注入、字段注入（官方不推荐）
- 处理多个同类型 Bean 的三种方式：`@Primary`、`@Qualifier`、注入 `List<Interface>`
- 注解配置类级别常用注解：`@Component`、`@Service`、`@Repository`、`@Controller`
- 注解配置注入常用注解：`@Autowired`、`@Resource`
- Java Config 常用注解：`@Configuration`、`@Bean`
- 五种 Bean 作用域：singleton、prototype、request、session、application
- request、session、application 仅在 Web 环境下可用
- prototype Bean 的销毁不归容器管，客户代码需自己清理

### 简答题考点

- **简述程序架构从硬编码到 IoC 的演进过程及各阶段解决的问题。** 答题要点：硬编码（数据与逻辑绑定）→ 命令行参数（数据外部化）→ 面向对象分层（关注点分离、但高耦合）→ 简单工厂（创建集中化、但工厂仍是硬编码依赖点）→ IoC 容器（创建与使用完全分离，声明式依赖管理）。
- **简述 IoC 的核心思想及实现基础。** 答题要点：核心思想是解耦合——将组件构建与使用分开；实现基础是面向接口编程 + 工厂模式 + 依赖注入。
- **对比 BeanFactory 与 ApplicationContext 的异同。** 答题要点：BeanFactory 是顶层接口，提供基础 IoC 功能，延迟加载，适合资源受限环境；ApplicationContext 是其子接口，启动时预加载单例 Bean，提供国际化、事件发布、AOP 等企业级功能，是企业级应用首选。
- **对比三种依赖注入方式的优缺点及适用场景。** 答题要点：构造器注入——强制依赖、不可变、易于测试，但依赖多时参数列表长；Setter 注入——灵活、适合可选依赖、能解决部分循环依赖，但依赖可能为 null、不适用于强制依赖；字段注入——代码简洁，但隐藏依赖、与容器强耦合、不可变、不推荐。
- **简述 Bean 的五种作用域及其适用场景。** 答题要点：singleton（默认，无状态服务/DAO）、prototype（有状态对象，每次新建）、request（每个 HTTP 请求）、session（每个 HTTP 会话）、application（整个 Web 应用）。
- **简述 Spring IoC 容器的四步使用流程。** 答题要点：导入依赖 → 创建配置文件 → 添加 Bean 配置 → 初始化容器并使用。

### 易混淆概念

- **IoC vs DI**：IoC（控制反转）是思想/原则，DI（依赖注入）是实现方式。IoC 是"做什么"（把控制权反转），DI 是"怎么做"（通过注入来反转）。两者常被混用，但 DI 是 IoC 的一种具体技术实现。
- **BeanFactory vs ApplicationContext**：前者是基础接口（延迟加载），后者是高级接口（立即加载 + 企业级功能）。不是替代关系而是扩展关系——ApplicationContext 继承了 BeanFactory。
- **容器级单例 vs GoF 单例模式**：Spring singleton 是每个容器一个实例，同一 JVM 中多个容器各有自己的单例；GoF 单例是每个 ClassLoader 一个实例。Spring singleton 不等于 Java 的 static singleton。
- **构造器注入 vs Setter 注入**：构造器注入用于强制依赖（没有依赖对象不可用），Setter 注入用于可选依赖（有默认值或用不用都行）。不是语法糖的区别，而是语义和契约的区别。
- **`@Component` vs `@Service` vs `@Repository` vs `@Controller`**：本质都是 `@Component` 的特化（元注解），都能让类被 Spring 扫描为 Bean。区别在于语义（Service 标记服务层、Repository 标记数据访问层、Controller 标记控制器）——语义差异使 AOP 切入点可以按层级精确匹配。
- **`@Autowired` vs `@Resource`**：`@Autowired` 是 Spring 注解，默认按类型匹配；`@Resource` 是 JSR-250 标准注解（javax.annotation），默认按名称匹配。`@Autowired` 可配合 `@Qualifier` 按名称精确匹配。
- **`@Primary` vs `@Qualifier`**：`@Primary` 标记在生产者（Bean 定义）上，声明"我是默认选择"；`@Qualifier` 标记在消费者（注入点）上，声明"我要特定的那个"。前者是推（push），后者是拉（pull），方向不同。
- **prototype 中的资源释放**：prototype Bean 容器不管销毁——这与 singleton 不同。singleton Bean 在容器关闭时会调用 destroy-method；prototype Bean 容器创建并注入后就不再跟踪，使用时必须手动释放资源。
